# C6 re-plan (2026-11-06): addendum to `2026-10-28-c6-per-machine.md`

Status: a re-plan. Nothing in it has been run on a machine. It keeps the old plan's procedure (sections 3 to 6 there) and changes what no longer holds. Facts say where they were read:
this repository at `origin/main` (`7ac64917`), the tags `v0.2.0` to `v0.3.0`, the published `v0.3.0` release and manifest, the live feed, and the build PC (read-only: its launchers, units and backup folders, and the fleet's worker socket, `GET` only).
Machines are named by role as in the old plan: the **control plane**, the **build PC** and the **third machine**. The fleet's names for them are not in this repository.

## 0. Summary

1. **The old plan's starting point is stale.** It assumed the machines run the release tool's ship of an early build (`0.1.1`). Today all three nodes report agent `0.2.3` at commit `5bcf7b8e` (2026-11-03, the merge of #221): 47 commits after `v0.2.3`, 76 commits before `v0.3.0`. None of the three runs the updater. They run a tree the release tool put under `~/product/.../live-ship-5bcf7b8` (build PC: read; the other two: reported by the fleet, install method not read).
2. **`v0.3.0` is the newest release and is already signed and published** (two owner approvals, 2026-11-05). `main` holds 27 more commits; four of them touch product code (`board-cli/src/cli.ts`, `node-agent/src/deliveries/{deliverer,views}.ts`, `node-agent/src/relay/status-ask.ts`), the rest are tests and docs. The release PR for `0.3.1` (#228) is open.
3. **Going from the running build to `v0.3.0` needs no database migration** and no protocol change: no migration file differs between `5bcf7b8e` and `v0.3.0`, the manifest says agent protocol `[1,1]`, schemas hub 29, fleet 18 (floor 7), node 8, connections 4, and the nodes offer protocol `[1]`. A `restore.sh` after the install therefore does not meet a changed schema (exit 4 in the old plan's table).
4. **Two things the old plan did not know would break the first real machine** (section 3): the launchers in `~/.local/bin` are wrappers that carry the hub address, node name and agent token, and a plain launcher has none of them; and the unit's drop-in `ship.conf` overrides `ExecStart`, so the install would leave the service on the old tree. Neither was in the rehearsal.
5. **Recommendation:** do not start a machine until two prerequisites are done: P1 (the board, memory, decide and job CLIs read their hub settings from files when the environment has none, and `morndo job …` works on every machine) and P2 (the rehearsal covers a drop-in that overrides `ExecStart`). Then adopt on the release that carries P1, which is `0.3.1` or later, not on `0.3.0`. Order: control plane, build PC, third machine. One compatibility interval is unproven (section 4, gate G1b). The owner's part is in section 5.

## 2. What changed since the old plan

- `v0.2.0` was the target; `v0.3.0` is out (2026-11-05, run `42021961006`, tag `a09c40d8`, eight assets, feed `latest.json` seq 6, `expiresAt` 2026-11-19T14:52Z). `stable.json` is empty; the plan stays on channel `latest`.
- `scripts/c6/backup.sh` changed since `0.2.0` (umask 077, `0700` for `restore.sh`, the node agent's `morndo-job-*` units never recorded or restarted). `arm-deadman.sh` and `db-backup.ts` did not. Take the scripts and their digests from the tag the machines will install, not from the old plan's `v0.2.0`.
- The old plan's step 2 runs `gh attestation verify` "where `gh` is logged in". `gh attestation` needs `gh` 2.51.0 or newer ([the README](../../README.md#the-gh-version-the-attestation-check-needs)); the build PC has 2.46.0, which has no such command. Run it on a machine with a newer `gh`, and compare `sha256sum install.sh` with the copy the machine verifies.
- The published-feed rehearsal (gate G1) names its version on the command line and was last passed for `0.2.0`: `npm run e2e:update-adopt-published -- --published <version>` must be run again for the release that will be installed.

## 3. What the real machines show that the rehearsal did not

**F1. The wrappers carry the lanes' settings.** On the build PC `morndo-board` and `morndo-memory` are small scripts that set `MORNDO_HUB`, `MORNDO_NODE`, the lane name from the tmux window, and `MORNDO_AGENT_TOKEN` (the manager's token for the manager's window, the shared lane token for every other). The CLIs read only the environment: without `MORNDO_HUB` and a token, `morndo-board` stops with "set MORNDO_HUB … and MORNDO_AGENT_TOKEN". The release's launcher is a plain `exec` of the Version's program (`scripts/release/launchers.ts`) and sets nothing. The old plan moves these files aside so the install can link its own (`install` refuses a real file, exit 78); the moment it does, every lane on that machine loses its board and memory commands, and so does the status line's follow-up. The control plane and the third machine very likely have the same wrappers (not read).
Two more release CLIs read only the environment: `morndo-decide` (`apps/board-cli/src/decide.ts`, the hub address and token; same message when they are missing) and `morndo-job` (`apps/node-agent/src/job-cli.ts`, the lane from `MORNDO_LANE`, which it does not take from tmux, and the token). The build PC has no wrapper for either today (neither name is in `~/.local/bin`; `morndo job` reaches it through the `morndo` forward, F3), so the install adds launchers that stop with the same kind of message. `morndo-keys` needs nothing: its wrapper is a plain `exec` of the connections program with no environment, so the release's launcher is equivalent and it keeps working (its check is in step 5).
**P1 (decided):** a small change in the four CLIs (board, memory, decide, job): when `MORNDO_HUB`, the token, the node name or the lane is unset, read them from files under `~/.config/morndo`: the two token files the wrappers read today (`agent-lanes.token`, `agent-manager.token`) and two new one-line files, `agent-hub` (the hub's address) and `agent-node` (the node's name), because the wrappers hold those two as constants in their text; the manager's token only for the manager's window (the window name decides, as the wrapper does), the lane token for every other window; the lane name from the tmux window as the board and memory CLIs already do (the job CLI gains it), asked about the CLI's own pane (`display-message -p -t "$TMUX_PANE"`): the CLIs' own lookup omits `-t`, so without the wrapper's export a lane would get the name of the window on screen, and could be handed the manager's token; an environment that is set wins; with the files missing, today's error text. Plus the spelling the lanes are told to type: `morndo job …` must reach the job program from the `morndo` launcher (F3). The wrappers then become unnecessary and the machines stop drifting from each other. A wrapper left in `~/.local/bin` is not an option: the next update would find a real file where it links. (A wrapper folder ahead of `~/.local/bin` in the lanes' `PATH`, with a restart of every lane, was considered and is not used: decision 3.)

**F2. A drop-in overrides the unit.** `morndo-node.service.d/ship.conf` on the build PC sets `PATH` (it must include `~/.local/bin`, or the engines are "not installed") and resets and sets `ExecStart` to the live-ship tree. `morndo install` carries over only `Environment=` and `EnvironmentFile=` lines of the *old unit file* into `before-morndo.conf`; it leaves other drop-ins alone (`apps/updater/src/adapters/services-systemd.ts`). Read from the code, not run: the service would keep starting the old tree while `morndo update --status` and the unit's first line say Morndo. The rehearsal's only drop-in (`limits.conf`) does not set `ExecStart`. The control plane's hub and fleet units probably have the same shape (not read).
Plan: the preflight lists every drop-in with an `ExecStart=`; the install step moves it into the backup folder and writes a drop-in that holds only its `PATH` line; the check after is `systemctl --user show -p ExecStart` naming the Version's launcher, and the fleet row naming the Version's commit. **P2** is to put a drop-in of that shape into the rehearsal so the plan is run once before it meets a machine.

**F3. `morndo job` on the build PC goes through a forward.** The build PC's `morndo` wrapper runs `morndo lanes` locally and sends every other command to the control plane over SSH. The key it uses allows one forced command, `morndo job …` (and `--help`), so `morndo job …` is the one thing that really goes through the forward today; `pair`, `devices`, `revoke` and `audit` are not reachable from the build PC and do not change. The release's `morndo` is the hub's program (`apps/hub/src/main.ts`): it dispatches `lanes`, `update`, `doctor`, `install`, `audit` and the console commands, and has no `job` branch; the job program is the separate launcher `morndo-job`. The lanes are told to type `morndo job start --notify … -- <command>` (the waker ask, `apps/node-agent/src/relay/status-ask.ts`), so after the install on the build PC every such call would fail until the spelling works. Plan: P1 includes a `job` branch in the `morndo` launcher that runs the job program, as it does for `lanes` and `update`; the forward is then not needed, the old wrapper stays only in the backup folder, and the forced key on the control plane is retired afterwards. What starts to work on the build PC: `morndo update --status`, `--check` and `doctor`. The callers of the forward (whoever starts jobs from the build PC) are the lanes there; the control plane's own `morndo job` is not read.

**F4. The release tool must stop shipping to these machines.** Its next run would swap `ExecStart` back to a live-ship tree. After C6, the machines move only by the updater; the tool's live-ship path is retired (or fenced) for them, and the old trees stay until the second release has been taken.

## 4. The plan

**Which release.** Adopt on the first release that contains P1 (`0.3.1` or later); `0.3.0` is not used, because on it F1 would break the lanes. The `0.3.1` release PR (#228) is open and would carry the 27 commits since `0.3.0`; whether it also carries P1 depends on P1 merging first. Every new release needs the owner's two taps (sign, then feed-sign); the Monday re-sign needs one.

**Gates before any machine** (all must hold, in this order):
1. G0: P1 and P2 are merged and in the release to be installed.
2. G1: `npm run e2e:update-adopt-published -- --published <that version>` passes with every check ok (about 13 minutes; last run on the third machine, which has rootless Docker).
   G1b: the compatibility interval of the order below is checked: (a) a read of the changes between the running build (`5bcf7b8e`) and the release in `apps/fleet`, `packages/protocol` and `apps/node-agent/src/relay` and of the manifest's agent protocol range against the nodes' offered `[1]`; (b) one rehearsal leg, in the same run as G1, that starts the release's hub and fleet against a node agent from the `5bcf7b8e` tree and shows the node connect, its lanes list, a message arrive, and a status line reach the board.
3. G2: the scripts and their digests from that tag are written on the card (old plan, section 3); the install is verified on a machine with `gh` 2.51.0 or newer.
4. G3: the feed is fresh: the feed's `expiresAt` (2026-11-19T14:52Z on the day this page was written) is at least five days away at the time of the first install; the Mondays 2026-11-09 and 2026-11-16 re-sign it.
5. G4: the owner's go to move the machines (section 5).

**Order: control plane, build PC, third machine** (decided). The updater never applies a Version above the control plane's (`skew()`, `node_ahead`), and a node ahead of its control plane is frozen, not just listed: the fleet refuses every `update.apply` to a node in `nodesAhead` (`docs/fleet-api.md`, the `/v1/rollout` notes), so putting a node first would leave it unable to take anything until the control plane catches up. With the control plane first the interval is the other direction: a new hub and fleet against nodes still on `5bcf7b8e`, from the control plane's step 7 until the build PC and the third machine are done. **That interval is unproven.** What is read: no file in `apps/fleet` or in the agent protocol differs between `5bcf7b8e` and `v0.3.0`, the nodes offer protocol `[1]` and `v0.3.0`'s manifest accepts `[1,1]`, and the hub's store reads the one extra event field of that range (`decisionDue`) only when it is present. The rest of the hub's changes in that range (the block gate, the merge flag) were not read for this. What is not: any run of it, and the adoption release itself (it will hold P1 and the 27 commits); gate G1b is the check. The cost of this order: the control plane is the machine whose loss the owner would notice, so it goes in the owner's night window with the manager awake for the first ten minutes, and its updater rollback is previewed before anything else (`morndo update --rollback --preview --json`). To keep the interval short the build PC and the third machine follow the same night or the next day, each after its ten minutes of health.

**Per machine, the old plan's steps 1 to 7 with these changes:**
- The preflight (old plan, section 3) adds: drop-ins with `ExecStart=` (F2), the wrappers that set `MORNDO_*` (F1), the `morndo` forward and its forced key (F3), the hub address and node name the old wrappers hold (to write `agent-hub` and `agent-node`), both token files present and private to the owner, the node status file shows nothing in flight and no lane mid-answer, `gh` version where the attestation runs, the fleet row (`curl --unix-socket … /v1/nodes`, `GET` only) noted before and after.
- Step 3, backup: as before, with the scripts from the chosen tag. The release tool's own record (`~/.local/share/morndo-backups/<date>-release-<sha>` with its `ROLLBACK.md`) stays; it is a second way back to the live-ship tree for as long as that tree is kept.
- Step 4, before the install: stop the units; move aside the real-file launchers (as before); with P1 in the release the lanes keep working through the CLIs' own file reading and `morndo job` through the launcher; move the `ExecStart` drop-in into the backup and write the `PATH` drop-in (F2); the old `morndo` forward goes with the other wrappers into the backup (F3, build PC); write `agent-hub` and `agent-node` (mode 0600) from the values the old wrappers held, before the install, and check them by running the lane's own commands in step 5.
- Step 5, checks, adds: `systemctl --user show -p ExecStart morndo-node.service` (and the hub and fleet units on the control plane) names the Version's launcher; the fleet row shows the Version's commit; from a lane window on that machine, by hand, `morndo-board list --mine`, `morndo-memory search …`, `morndo job list` and `morndo-keys --version` answer, and `morndo-decide` (the manager's tool) answers a read from the hub; one lane ends a turn with a status line and the board moves the task; the hook relay answers on its port; `systemctl --user --failed` is empty.
- Step 7, ten minutes healthy, as before. Control plane only: set the window (`morndo update window 03:30-05:00`) and `MORNDO_ORIGIN` as in the old plan.

**What lanes see during each step**

| Machine | Lanes | Hub and app | Window |
|---|---|---|---|
| Control plane | the fleet and node restart: every machine's lanes show offline for about a minute and reconnect; messages in flight are spooled; the manager pane lives in tmux and stays | the app is unreachable about a minute; the board is unreachable for the same time, so a status line posted then waits | the owner's night window |
| Build PC | the node agent restarts (seconds); the hook relay on its port does not answer while it restarts, so a lane ending a turn at that moment can miss its status ask; the lanes' own commands (`morndo-board`, `morndo-memory`, `morndo job`) unchanged with P1 | none | day, when `inFlight` is empty |
| Third machine | as the build PC; no lane command changes | none | day |

The lanes' tmux servers and the node agent's `morndo-job-*` units are outside the units' control groups and are not stopped (old plan, step 4). The build PC hosts the lane that runs this procedure and the manager's helpers: whoever runs steps 1 to 6 there does it from a window other than a lane that is mid-answer.

**Backups and rollback per machine.** As the old plan's section 5, with the dead-man's switch armed before the install (60 minutes). Additions: the backup folder holds the moved `ExecStart` drop-in and the wrappers, so `restore.sh` puts back unit, drop-ins and launchers together; the restore does not meet a changed schema because none changes (section 0, item 3); after a restore, a retry needs the updater's three folders removed (old plan). Once the switch is closed, the way back is the updater's `morndo update --rollback`; the first real one is run on the control plane in the daytime, after the release after the adoption release has been taken, as in the old plan.

**After.** The next release after the adoption release is the proof of the auto-update (old plan, section 6): the control plane takes it inside its window, the nodes after the 30-minute soak. Retire the live-ship path for these machines (F4); remove the old trees only after that second release and the owner's word.

2. **Not read, to read before the preflight of each machine** (a lane on that machine reads them): the control plane's and the third machine's units and drop-ins, wrappers (including whether they have a `morndo job` forward and a `morndo-decide`), `ship.conf` equivalents, `~/.config/morndo`, and their `gh` and `systemd` versions.

## 7. Decisions (manager, 2026-11-06)

The answers to the six questions this page asked, in their order:

1. **P1.** The board and memory CLIs read the hub address, the node name and the token from the files under `~/.config/morndo` when the environment has none. The manager's token is used only for the manager's window; every other window gets the lane token, exactly as the wrappers decide today. The environment still wins when it is set. Scope widened after the review of this page: the decide and job CLIs too, and `morndo job …` through the `morndo` launcher (F1, F3); `morndo-keys` needs nothing.
2. **Order:** control plane first, in the owner's night window, with the manager awake for the first ten minutes; then the build PC, then the third machine.
3. **Release:** the first release that carries P1 (`0.3.1` or later). `0.3.0` is not used.
4. **Who:** the lane on each machine runs its own steps; the control plane's with the manager watching. The attestation check runs on a machine with `gh` 2.51.0 or newer, asked for at gate G2.
5. **F4 agreed:** the release tool's live ship is retired (fenced) for a machine once it is on the updater.
6. **Reads:** the per-machine reads of section 6 happen right before each machine's preflight, by a lane on that machine.

The work in order, each its own pull request: this page; P1 (the CLI fallback); P2 (the rehearsal gets a drop-in that sets `ExecStart` and `PATH`, and the adopt scenario proves the install moves it into the backup and the unit runs the Version's launcher). No machine starts before G0 to G4 of section 4.
