# C4-5: the rehearsal of the first release (a plan, for review)

Status: a plan. Nothing in it is built, run, pushed or changed. It extends section 2 (row C4-5) and section 5 of `docs/plans/2026-10-23-c4-c6.md`. Facts say where they were read (2026-10-24; this repository at `4a0274cf` plus the open C4 pull requests #123, #126, #128, #129, #131, #132, #134 and #135; the test repository `morndo/morndo-release-test` read through the GitHub API, read-only).

## 0. Summary for the owner

**What it gets done:** one full run of the release pipeline, on a scratch repository with throwaway keys, that exercises every job that has never run live: the feed and Pages jobs, the weekly re-sign, the withdrawal and the promotion, followed by a real `morndo install`, an update, a rollback and a withdrawal watched from clean machines that read the real Pages feed and the real release assets. Each defect it finds becomes a pull request with its own test. **The first real release does not start before one rehearsal has passed end to end on the final candidate tree.**

**Decisions, each with the answer I recommend**

1. **Where:** the existing bench, `morndo/morndo-release-test` (public, throwaway keys, "nothing should install from it"). No new repository. Section 2.
2. **What the bench runs:** the real pipeline, byte for byte, except a short named list of differences (section 2). The list is produced by a script and a test, not by hand, because every defect fix needs another rehearsal. Section 2.
3. **The waits are shortened in the bench only:** the seven days of a promotion become 20 minutes (two constants and one shell check). The 14-day Feed lifetime is not shortened (it is pinned in two places); its expiry is covered by the existing tests and the Monday ritual, not by the rehearsal. Section 2 and 6.
4. **The owner's part:** the setup of the bench's environments from `docs/release-settings.md`, run by the owner or the Mac (this also rehearses that document, minus the release App's rules, which the bench cannot have), Pages switched on, one throwaway key stored as a secret, and **about ten taps as the second account** in one or two sittings. Section 4.
5. **Machines:** clean containers of the existing systemd test image, with real network. **Never** the owner's three machines (they are C6). Section 3.
6. **Not rehearsed, accepted:** Release Please's own pull request and tag (the bench has no release App; its stand-in produces the same outputs), the real seven and fourteen days, macOS and Linux arm64 (manual QA, the other plan's decision 8). Section 6.

**Time:** about **two lane days** after C4-0 to C4-6 are on `main` (one for the overlay script and the setup check, one for the run, in parallel with the owner's taps), plus whatever the defects it finds cost. **The wall clock of one attempt is about one working day** (the builds and the two feed waits dominate, and the taps arrive in two or three sittings), **plus a re-run per defect** (a fix, its review, and another day's attempt from the first step it touches). The estimate of the larger plan stands.

## 2. The bench: what it is today and what it must become

**Today (read 2026-10-24).** Public repository, created 2026-10-21, default branch `main`, no rulesets, no Pages, no variables, no secrets at repository level, one environment (`release`, no reviewer, administrators may bypass). Its last commits say `chore: bench: morndo fix/release-pipeline-bench at eca3727 with the overlay`: the tree stands at the pipeline branch's state of 2026-10-22, **before** the settings commands, the withdrawal and the promotion. The overlay (the bench's own trust files, a stand-in for the `release-please` job, the bench's root signer, the feed and Pages jobs removed, the tests that pin production files removed) was applied **by hand** each time; there is no script.

**What it must become.** The bench tree is the candidate commit of `morndo/morndo` plus an overlay, and the rehearsal means something only if the overlay is small and exactly known. The overlay, each line with its reason:

| Difference | Why it is needed | Whose job |
| --- | --- | --- |
| `trust/*` are the bench's throwaway public keys; the private halves are secrets of the bench's `release` and `feed` environments | the production keys must never reach the bench | exists for release; the feed key is new |
| `release.yml`: the `release-please` job is the stand-in that makes the tag and the draft the way Release Please does and produces its outputs (`release_created`, `tag_name`); **every other job, including `feed-prepare`, `feed-sign`, `feed` and `pages`, is the real one** (today they are cut) | the organisation does not let Actions open pull requests and the bench has no release App | exists, narrowed |
| `ROOT_ALLOWED_SIGNER` in `release.yml` is the bench's root key | `trust/keys.json.sig` in the bench is signed by it | exists |
| `feed.yml`, `withdraw.yml`, `promote.yml` are copied **unchanged** (today removed) | they are what is rehearsed | new |
| every other workflow in `.github/workflows/` is removed (the old bench removed `ci.yml`, `commit-traces.yml`, `negative-controls.yml`, `secrets.yml` and `transcription-plugin.yml` as well; they run production checks the bench cannot pass or should not run) | only the four release workflows are rehearsed; the others would fail or spend minutes on every push | exists, now an allow-list of four |
| `PROMOTION_WAIT_MS` (`scripts/release/feed.ts`) and `PROMOTE_MIN_AGE` (`scripts/release/check-signing-feed.sh`) are 20 minutes instead of seven days | a promotion cannot be rehearsed over a week; the refusal and the acceptance are both run under the shortened value | new, named in `BENCH.md` |
| the test files that pin production values are removed: `workflow.test.ts`, `signing.test.ts`, `apps/hub/test/val-b12-e2e-listed.test.ts`, `plugins/transcribe-whisper-cpp/test/install.test.ts`, and now `apps/updater/test/docs.test.ts` (it pins the README's key line to `trust/`, which the bench replaces) and `scripts/release/release.test.ts` (three of its tests assert the seven-day promotion wait: found by running the whole `units` suite on an overlaid tree, where exactly those three failed). The list is a data file the script reads, and a test pins it; the bench's `units` job runs the whole unit suite, so a test that starts failing there because of a production value is added to the list in a pull request | they assert the production wording and keys | exists, two files added (C4-5a, #137) |

**Production cannot take the overlay by accident:** a test in `scripts/release/workflow.test.ts` pins `PROMOTION_WAIT_MS` (seven days), `PROMOTE_MIN_AGE` (604800) and the 14-day lifetime by value (on #132, `ffd4b6fc`), and the overlay removes that file from the bench, so an overlay edit that leaked into production fails CI, and the bench does not run the pin.

**Not changed on purpose:** the Feed's 14-day lifetime (the shell check requires exactly `1209600` seconds, and `feed.ts` writes it; shortening it means editing two places and a rule the production run depends on). The real versions of the changed constants are covered by the unit tests; the rehearsal says so in its record.

**The overlay as a script (C4-5a, one lane day).** `scripts/release/bench-overlay.sh <commit>` builds the bench tree from a commit and applies exactly the table above; its test fails if a workflow other than `release.yml`'s `release-please` job differs from the source, or if the overlay touches anything not in the table; it prints the diff of every workflow and `scripts/release/**` file against the source commit, which becomes part of the rehearsal's record and what a reviewer reads. Every re-run after a defect fix reuses it. It never pushes; pushing the result to the bench is a separate, named step (section 3, step 2).

**Version numbers.** A published release in the bench is immutable and locks its tag (`BENCH.md`), so each run uses the next free version. After `v0.1.0` and `v0.1.1`, the first rehearsal release is `0.1.2` and the second `0.1.3`; a re-run after a defect uses the next, and the numbers in this plan are examples.

## 3. The run

Marked **[tap]**: the owner, signed in as the second account, on a browser profile or phone that no lane uses. **[owner]**: a setting only the owner or the Mac changes. **[word]**: the manager's word first.

0. **Preconditions.** C4-0 to C4-4 and C4-6 merged to `main` (the candidate tree is `main` before release pull request #99 merges); the reviews of those pull requests done; no production release or feed run in progress; the manager told that the bench is about to run.
1. **[owner] Bench setup.** On `morndo/morndo-release-test`, run the setup steps of `docs/release-settings.md` with the bench's ids: environments `release`, `feed`, `promote`, `withdraw` (reviewer: the second account, Prevent self-review on, branch `main` only), the `github-pages` environment (`main` only, no reviewer), the feed-branch ruleset and the `main` ruleset with code-owner review; switch Pages on with GitHub Actions as its source; store the bench's throwaway feed key as `FEED_SSH_KEY` in `feed` only (its private half is made by the lane in the scratch area and handed over through the owner's own channel, never printed, never committed). The bench has no release App and its stand-in makes the tag with the run's own token, so **the bench gets no tag ruleset and no `release-please` environment**: the tag ruleset would block the stand-in. Then run `scripts/release/check-release-settings.sh --repo morndo/morndo-release-test` (with the bench's reviewer id); its output before and after is evidence (P9), and the lines it still fails afterwards must be exactly the ones about the App, named in the record. Any other failing line is a defect of the setup or of the check. Any step of the document that fails as written is a defect of the document (a pull request).
2. **[word] Refresh the bench.** The lane runs `bench-overlay.sh` on the candidate commit, reads the diff it prints, and pushes the result to the bench's `main`. This is the only push the rehearsal makes, and it is to the scratch repository. The push starts a `Release` run.
3. **P1, P2.** The run: `signers`, the stand-in, `build` and `units`, `assemble`, then `sign` waits **[tap]**; `publish`, `outside`, `ship`, `published`, `feed-prepare`, then `feed-sign` waits **[tap]**; `feed` and `pages` run on their own. The lane records each job's conclusion and fetches `latest.json`, its signature and the key set from the bench's Pages URL and verifies them with the key set the way a machine does (`scripts/release/feed-site.ts`). **Then, at once, while the release is younger than the 20-minute wait, `promote.yml` on it [tap] `promote`: it must refuse and name the age** (the lane notes the listing commit's time and the attempt's time, so the record shows it was young). The owner has the `promote` tap ready before the feed job starts. If the 20 minutes were missed, the same refusal is made right after the second release's listing at step 5, which is never promoted.
4. **P3.** A clean container of the existing image. **Controls, each checked from `docker inspect` before the first command runs, and recorded:**
   - **not `--privileged`** (`HostConfig.Privileged` is false);
   - **the capabilities are exactly the harness's own** (`e2e/update.e2e.ts`, `e2e/update-vm/`): Docker's default set, plus `SYS_ADMIN` (`--cap-add SYS_ADMIN`; systemd as PID 1 needs a writable cgroup tree, and Docker mounts it read-only without `--privileged`, so the image's entrypoint remounts the container's own cgroup namespace writable), minus `AUDIT_WRITE` (`--cap-drop AUDIT_WRITE`, so systemd does not try to audit), with `--cgroupns=private` and `-e container=docker`; `CapAdd` is `[SYS_ADMIN]` and `CapDrop` is `[AUDIT_WRITE]`, nothing else;
   - **no devices** (`HostConfig.Devices` empty) and no device cgroup rules;
   - **no `docker.sock`** and no other mount from the host: `Mounts` holds only the container's own tmpfs mounts (`/run`, `/run/lock`, `/tmp`), no `Binds`, no volumes; files go in with `docker cp`;
   - the network is the default bridge, not `host` and not another container's; no published ports; no host PID or IPC namespace; no Tailscale or other VPN client in the image or on the container;
   - **the host is not a production node**: not `srv01`, not the build PC, not the owner's control plane, and not any machine `lanes` lists as a node. The containers run on a machine that is none of those (section 4);
   - only the control-plane role is ever installed (a `node` install would look for a control plane to join);
   - `MORNDO_UPDATE_FEED` and `MORNDO_RELEASE_BASE` are set before `install.sh` runs, and the run stops if either is missing;
   - the container carries the harness's label, so cleanup can assert nothing is left. The README's verify-first block, with the bench's repository path and key line substituted, run as written; then the install. `install.sh` downloads from production's release address unless `MORNDO_RELEASE_BASE` names another (its default is `github.com/morndo/morndo/releases/download/v<version>`), so the run sets it to the bench's release. The machine's environment carries `MORNDO_UPDATE_FEED` set to the bench's Pages URL (https, as the updater requires). **A machine has no other way to find the bench**: both defaults are production's, which the rehearsal never uses; a step run without the two variables is a mistake to stop on, not to continue. Checks: `morndo update --status`, `morndo doctor`, the fleet lists the machine online, a lane starts. `docs/design/updates/manual-qa.md` steps 1 and 3 are filled in the lane's notes (never in the repository).
5. **P4.** A second release through steps 2 and 3 (**two [tap]s**). On the machine: `--check`; `--status`; mode `apply` with no window, and the updater's own boot check (a restart of its unit; if a restart does not trigger one, that is itself a finding) stages and applies it; the alert for the check that was already failing is read; probation commits. Then a window that excludes now: an automatic apply waits, `morndo update --yes` does not (checklist 19).
6. **P5.** `morndo update --rollback --preview --json`, then `--rollback`; `--status` shows the first release current and the second halted.
7. **P6.** `feed.yml` by hand on `main` **[tap]**; the Feed's number is one higher, the signature verifies, Pages serves it, the machine's next `--check` is clean.
8. **P7.** `withdraw.yml` on the second release **[tap]** `withdraw`, then **[tap]** `feed`; the Feeds mark it and keep it; a second clean container installing `latest` lands on the first release; on the first machine `morndo update --to <second>` is refused (checklist 16 and 17).
9. **P8.** `promote.yml` on the first release, now past the shortened wait: **[tap]** `promote` then **[tap]** `feed`; `stable.json` lists it; a third clean container with `--channel stable` installs it (checklist 18). 10. **P10.** The README's update, channel, pin, mode and window commands, run once each on the first machine, with the exit code and output noted.
11. **Close.** Containers removed; the harness's own assertion that nothing carrying its label is left running; the secret `FEED_SSH_KEY` and the reviewer settings left as they are (the bench stays set up for re-runs) unless the owner wants them removed; the lane's record goes to the private QA notes with the job conclusions, the feed files, the diff the overlay printed and the check script's before and after.

**Taps:** release 2, second release 2, re-sign 1, withdrawal 2, promotion 3 (one refused) = **10**, each about a minute. A cheaper rehearsal leaves `promote` and `withdraw` without a reviewer in the bench (7 taps: the refused promotion then stops without a tap), but then it no longer shows that those runs wait; the settings check would still show the production configuration. **Recommended: all ten**, in one sitting of about an hour spread across a working day, because the taps are the part of the real procedure the owner will repeat for years.

## 5. Rollback and clean-up

| What | How it is undone |
| --- | --- |
| Bench commits, branches, the `feed` branch | the bench is scratch: the owner may delete the `feed` branch to start the next rehearsal from nothing (the first release in production will also start from no `feed` branch, so the first run is the one to keep as the model) |
| Bench releases and tags | immutable by design (`BENCH.md`); each re-run takes the next free version; they stay |
| Bench Pages | the owner turns it off, or leaves it; it holds only test documents signed by throwaway keys |
| Bench secrets and settings | the owner removes them after the last rehearsal; the keys are throwaway and never used elsewhere |
| Containers | removed by the lane; the harness label check proves it |
| A step that fails | stop; no later step is run on top of it; the defect becomes a pull request with a test; the run restarts from the earliest step that fix touches, on a new version |

## 6. What it does not prove, and the defects to watch for

**Not proven by this rehearsal (accepted, written into its record):** Release Please's own pull request, its tag and its App token, and the settings that exist for the App (the tag ruleset limited to the App, the `release-please` environment and its secrets: the stand-in matches Release Please's outputs, the first real run is its first live run, and it stops at `sign` for a tap before any key is used); the real seven-day wait and the real 14-day expiry (unit tests and the Monday ritual); macOS and Linux arm64; the adoption of an older setup on the owner's three machines (C6-0); a hard power loss; the phone's Settings page. **Also not proven, and why:** (a) the owner path **passing** and an update **rolled back by it** on a real control plane: a container has no manager lane and no https origin, so `owner_manager_lane` and `owner_origin_ready` can only be seen failing or unset there (C6's first control-plane step is where they are first seen passing); (b) the **boot apply** (the next boot after a commit judging the stored baseline with the owner path left out): covered by unit tests only; (c) the **literal README install path**: its block names the production repository and key, which do not exist until the first release, so the rehearsal runs it with the bench's repository path and key line substituted; (d) the **production** tag ruleset, the `release-please` environment and its secrets, and the admission of the release App's identity by the commit-traces check (the bench has no such workflow, no App and no tag ruleset); (e) the **node role** (a node never newer than its control plane, `--to` above it refused): the rehearsal installs control planes only.

**Places a defect is most likely** (a guess, labelled as one; each is a thing to look at first): the first feed commit when no `feed` branch exists; the Pages deployment's permissions and environment in an organisation's public repository; the preparation's calls to the GitHub API with the run's own token; the soak read from real commit dates; and **how a machine is told where the Feed is**: the updater's default is production's address, and the only override is the `MORNDO_UPDATE_FEED` environment variable, which the rehearsal sets for its containers. If nothing but an environment variable can point a machine elsewhere, that is worth a line in the README and possibly a settings key; the rehearsal reports it either way.

**Risks.** A rehearsal that passes on a hand-made overlay would prove less than it seems: hence the script, the printed diff and the test that pins the overlay's size. A re-run costs a version number and about an hour of the owner's taps: the plan expects at most two re-runs. The bench's Actions minutes are free (public repository); the billing stop that holds `morndo/morndo-private`'s CI is that repository's, and the bench's runs of 2026-10-22 started normally. A reviewer-tap is only evidence that the run waited if the run's log shows the wait; the lane records the approval times.

## 7. What it must never touch

- **The production repository `morndo/morndo`:** no workflow run or dispatch, no tag, no release, no environment, secret, ruleset, Pages setting or `feed` branch change. The only thing the rehearsal reads there is the candidate commit.
- **Real keys:** the release key, the feed key, the root key and the release App's secrets are never copied, mounted or used; the bench's keys are made for it and are different keys with the same identities' names only because the pipeline names them so.
- **The owner's machines** (the control plane, the build PC, the third machine) and every real fleet: no container joins a real fleet; nothing runs `morndo install` outside a container.
- **The production Feed address:** no rehearsal machine is given it, and no bench file is published anywhere a real machine looks.
- **Real data:** no customer or client material in a release, a Feed, a container or a record; the bench tree is a copy of this public repository.
- **The shared browser:** the taps are made by the owner in their own browser; no lane drives a sign-in.
- **Any other `main`:** the only push is the bench's, step 2, and only after the manager's word.
