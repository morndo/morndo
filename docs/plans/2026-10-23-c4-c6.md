# C4 and C6: the first release, and the three machines onto the updater (a plan, for review)

Status: a plan. Nothing in it is built, run or changed. Facts say where they were read (2026-10-23, this repository at `4a0274cf`, and the repository's settings through the GitHub API, read-only).

## 0. Summary for the owner

**What this plan gets done:** the first release (0.1.0) approved and published, the three machines moved onto the updater one at a time, and a second release (0.1.1) that they take by themselves. C5 (the release verifier) is held and comes back rescoped later.

**Decisions, each with the answer I recommend**

1. **Who approves a release until C5 exists?** You, signed in as the second GitHub account (the release reviewer), on your own phone or browser profile, never on a machine a lane can use. Prevent self-review stays on. Why in section 1.
2. **Three approvals per release, and two every Monday, are set up today** (the environments `release`, `feed` and `github-pages` all name that reviewer). Remove the reviewer from `feed` and `github-pages`, keep it on `release`: one tap per release, none for the weekly re-sign. Why in section 1.
3. **Order of the three machines:** control plane first, then the build PC, then the third machine, not the third machine first. The updater's own rule is that a node is never newer than its control plane. Section 3.
4. **A window for automatic applies on the control plane:** 03:30 to 05:00 local, so the update never restarts the hub in your working day.
5. **The first release contains** the settings commands and the withdrawal workflow (both merged first); the promotion workflow follows within the seven days a release waits on `latest` before `stable`.
6. **Linux arm64 manual QA** on the owner's Mac, in an arm64 Linux container of the existing test machine image (Apple silicon runs those natively), unless you have an arm64 server.

**Time:** about **ten working days** from your go to "the machines took 0.1.1 by themselves": the first release is installable on about day 6 to 7, the three machines are on the updater by about day 9, and 0.1.1 proves the auto-update on about day 10. **"This week" covers the first release at best, not the machines.**

## 1. Who approves a release until C5 exists

**Facts**

- A release run (`.github/workflows/release.yml`) stops at `sign` in the environment `release`, and its later feed and Pages jobs stop again in `feed` and `github-pages`. The settings, read through the API: all three environments list **one required reviewer, the second GitHub account, with "Prevent self-review" on**, and allow the branches `main` and `v*`.
- Every merge to `main` is made by the maintainer account, so a run started by that merge was started by that account; with Prevent self-review it cannot approve it. The reviewer is a different account, so **the owner can approve as that account** and nothing in the settings blocks it.
- Builder lanes run as the maintainer account (`gh` on the PC). That is why the reviewer is a separate account: a lane can never approve a release.
- `feed.yml` re-signs the Feeds every Monday at 06:17 UTC: `resign-sign` waits in `feed`, then `pages` in `github-pages`. The design keeps the feed key online precisely so this needs no human (design §9.5, decision Q3), and the Feed expires after 14 days, so **a fortnight without a tap would let it expire** and every machine would report that something holds updates back.

**Options for the approver**

| | Option | What it costs |
| --- | --- | --- |
| a (recommended) | **The owner approves as the second account**, in a browser profile or app that is not on any machine a lane can use | one account switch per release; no settings change; Prevent self-review stays; C5 later takes over the same reviewer seat with no change |
| b | **The release App merges the release pull request**, so the maintainer account can approve | the App needs a bypass of the `main` ruleset (it can approve nothing, and the ruleset wants a review): that gives a token inside a workflow the power to merge anything |
| c | **Turn Prevent self-review off and list the maintainer account** | the account lanes run as could approve its own release; it removes the control the separate account exists for |
| d | A third account | the same as (a) with one more account to guard |

**Recommended:** (a), and **take the reviewer off `feed` and `github-pages`** (keeping it on `release`). The release key is then used only after a tap, which is the design's gate (Q3); the feed key signs, and Pages publishes, what that approved run produced, without further taps, and the weekly re-sign needs nobody. Both environments stay limited to `main`. Taps per release: **one**, as the account, at the moment the key is used. (If the owner prefers to keep all three reviewers for the first release as a careful start, the run book in section 4 lists the three taps; the weekly re-sign must then be tapped, or moved to an environment of its own, before the first Monday after the release.)

## 3. C6: one machine at a time

**The rehearsal first (C6-0, 2 days, in parallel with C4).** The throwaway-machine harness (`e2e/update-vm`) installs a release on a clean machine. It does not yet start from a machine set up the way these three are (units running `apps/<service>/src/main.ts` from a release folder, wrappers in `~/.local/bin`, databases in place). A scenario that builds exactly that state and runs `morndo install` over it proves the adoption before a real machine is touched: units adopted, databases opened, lanes' processes kept, health green, and the old release folder still on disk for a way back.

**Order: control plane, build PC, third machine.** The 10-21 plan said the third machine first (the least important, as a canary). The updater's rule is that a node is never newer than its control plane (`skew()`, `node_ahead`; the Rollout starts with the control plane): a node installed at 0.1.0 under a control plane still on the old build would be newer than it, and the design has only tested the other direction. The hub restarts on the control plane in every order, so putting it first buys the invariant and costs nothing extra; the rehearsal and the backup are what make that safe. If the owner prefers a real canary first, run a ten-minute spike in the harness (a node at 0.1.0 joining a control plane on the old build) and go by its result.

**Per machine (about 30 to 45 minutes each):**

1. **Before:** the machine runs the same build as the others (all three run `4a0274cf`); nothing else is releasing; for the control plane, tell the manager.
2. **Backup, written down:** the unit files and drop-ins (`~/.config/systemd/user/morndo-*.service*`), the wrappers (`~/.local/bin/morndo*`), and each database by SQLite's online backup (the release tool's method), into `~/.local/share/morndo-backups/<date>-c6-<machine>/` with a `ROLLBACK.md` of the exact restore commands.
3. **Install:** download `install.sh` and its signature from the release, verify them with the real key line, then `sh install.sh --role control-plane|node --channel latest --signers <file>` (the owner's fleet writes `latest`; the default for everyone else stays `stable`). It verifies the Manifest, installs through the Feed, adopts the units, starts the services and runs the health checks.
4. **Checks after each machine:** `morndo update --status` shows updater-managed, `latest`, current 0.1.0; `morndo doctor` clean; the fleet lists the machine `online` on the release's commit; the lanes of that machine are online; a long message (about 28,000 characters) sent to a scratch lane arrives and is answered (the probe of the bootstrap plan); on the control plane also the hub's `/api/health` with the new commit and schema, https ready, and the manager answering.
5. **Rollback trigger:** the install exits non-zero, a health row is wrong after 5 minutes, the node does not rejoin in 3 minutes, or the manager cannot be reached through the hub. **Rollback:** restore the backed-up units and wrappers, `systemctl --user daemon-reload`, restart the units (they point at the release folder that is still on disk), and restore a database only if the old code refuses the new one (the migrations between the builds so far were additive, and the old code understands the schema floor; the release notes list any that are not). Rollback is minutes. The updater's own `--rollback` is not the way back from the first install: it has no earlier updater-managed Version to go to.
6. **Order of the confirmations:** do not start the next machine until the previous one has been healthy for 10 minutes.

**What the updater does on the control plane afterwards.** With mode `apply` it checks the `latest` Feed on its tick; a newer verified Release is staged and applied at a **safe point** (nothing in flight that a restart would break: deliveries and jobs), restarting fleet, hub and node in order, then judging health in probation; a failed check rolls the control plane back by itself and **halts the Rollout** so the nodes never take it. The nodes apply after the control plane commits, once the 30-minute soak (design §7) and a random delay of up to 15 minutes have passed. The hub is the owner's main channel and the manager's control plane, so: the manager's pane lives in tmux and survives; what the owner sees is a gap of the length of the restarts. Measured today, a release moved all three units on the control plane in about 4 seconds of restarts, and the hub took about 6 seconds more to finish its first look. Decision 4 (a window of 03:30 to 05:00) keeps even that out of the working day; a window never blocks an update the owner asks for with `morndo update`.

## 4. Run book: from #99 green to all three machines on 0.1.0 and then 0.1.1

Taps by the owner are marked **[tap]**.

1. **Preconditions:** T-411 merged and #99 rebased and green (`ci`, `fleet`, `traces`, `gitleaks`, release checks) on the merged tree; C4-1 and C4-2 merged before #99; C4-5's rehearsal passed; the owner's one-time setup is in place (read today: the three environments, Pages enabled, the repository variable `MORNDO_RELEASES_ENABLED`, the trust files).
2. **Merge #99** (the release App opened it; the maintainer account may approve and merge it). **[tap]** This starts the `Release` run.
3. **The run:** `signers`, `release-please` (tag and draft), the builds for Linux x64, Linux arm64 and macOS, the unit tests, `assemble`, then **`sign` waits: [tap]** the owner approves as the second account (decision 1). Then `publish`, `outside` (the check from outside the signing job), `ship` (the draft becomes the immutable release), `published` (`gh release verify` and `verify-asset`), `feed-prepare`, `feed-sign` and Pages. With the recommended settings there are no more taps; with all three reviewers kept, **[tap]** for `feed-sign` and **[tap]** for the Pages deployment.
4. **Check the release from outside:** the README's verify-first block with the real key line on `install.sh`; `gh attestation verify` on the assets; the Feed fetched from the Pages URL and verified with the key set; `morndo update --check` on a throwaway machine says what the Feed offers.
5. **Manual QA (the owner's Mac), before any real machine** (ADR-0019, "Verification this implies" 5): Linux x64, Linux arm64 (decision 6) and macOS, each from a clean machine by the README commands: verify-first install by role, pair a phone, start two lanes, `morndo update --check`, `morndo doctor`, a rollback preview. Results go to the private QA notes, not this repository. A blocking defect stops the plan here; the release stays on `latest` only until it is withdrawn with C4-2's workflow.
6. **C6** on the control plane, then the build PC, then the third machine (section 3).
7. **0.1.1**, a small real change through the same run (merge, approve, wait): the control plane takes it at its window, the nodes follow after the soak, and `morndo update --status` on each machine shows 0.1.1. **That is the auto-update running.** The rollback drill (`morndo update --rollback --preview`) is read on one machine, not run.
8. **Promotion** (C4-3) after seven days on `latest`: **[tap]** as the second account on the `promote` approval; the owner's own machines are already on `latest`.

## 5. Risks and what this plan does not do

- **Never run live:** the feed and Pages jobs, Release Please's own release, `morndo install` against a real Feed, and adoption over a release-tool setup. C4-5 and C6-0 exist to run each once before it matters.
- **The `latest` channel has no verifier gate** while C5 is held: a release reaches the owner's machines after CI, the manual QA and one tap. That is the accepted trade of putting the owner's fleet on `latest`; a withdrawal only marks a release, it does not move machines already on it.
- **The review of release content:** with C5 held, nothing automatic checks that every pull request in a release was reviewed; the owner's tap is that check.
- **Time:** the estimate assumes three lanes in parallel and no failure in the rehearsals; a defect found in C4-5 or C6-0 adds days, not hours.
- **The release tool** (used for the bootstrap) keeps releasing until C6 is done, and stays unused after it.
