# C4 and C6: the first release, and the three machines onto the updater (a plan, round 2, for review)

Status: a plan. Nothing in it is built, run or changed. Facts say where they were read (2026-10-23, this repository at `4a0274cf`, and the repository's settings through the GitHub API, read-only). Round 1 proposed dropping the reviewer from two environments; the review showed that would leave the feed key behind a branch rule only, with builder lanes running as an account that can push. This round keeps the human where the keys are used.

## 0. Summary for the owner

**What this plan gets done:** the first release (0.1.0) approved and published, the three machines moved onto the updater one at a time, the owner's own path (the app, https, the manager) judged by the updater on the control plane, and a second release (0.1.1) that the machines take by themselves. C5 (the release verifier) is held and comes back rescoped later.

**Decisions, each with the answer I recommend**

1. **Who approves a release until C5 exists?** You, signed in as the second GitHub account (the release reviewer), on a phone or browser profile that no lane can use. Prevent self-review stays on. Section 1.
2. **Which environments keep that reviewer:** `release` (the release key), `feed` (the feed key) and the new `promote` and `withdraw`; **not** `github-pages` (it serves documents that clients verify). That is **two taps per release and one every Monday** for the weekly re-sign, which must happen within 14 days or the Feed expires. Section 1.
3. **Close the tag route:** each of those environments allows branch `main` only (today they also allow tags `v*`), and a tag ruleset lets only the release App create `v*` tags. A script that checks all of this runs before every release. Section 1.
4. **Order of the three machines:** control plane, then the build PC, then the third machine. A node is never newer than its control plane. Section 3.
5. **Apply window on the control plane:** 03:30 to 05:00 local, set in C6 (the default is none, so it would apply at any hour). Section 3.
6. **Owner-path checks** in the control plane's probation (the app is served, https answers, the manager is reachable through the hub) before any automatic apply is allowed on the control plane. Section 2.
7. **The first release contains** the settings commands, the withdrawal workflow and the owner-path checks; the promotion workflow follows within the seven days a release waits on `latest`, and that wait is measured from when the release was published, not from its commit date. Section 2.
8. **Linux arm64 manual QA** on the owner's Mac, in an arm64 Linux container of the existing test machine image, unless you have an arm64 server.

**Time:** about **eleven working days** from your go to "the machines took 0.1.1 by themselves": the first release is installable on about day 7, the three machines are on the updater by about day 10, and 0.1.1 proves the auto-update on about day 11. **"This week" covers the first release at best, not the machines.**

## 1. Who approves a release until C5 exists, and what stands behind the keys

**Facts (the repository's settings, read through the API on 2026-10-23)**

- A release run (`.github/workflows/release.yml`) stops at `sign` in the environment `release`; its feed and Pages jobs stop again in `feed` and `github-pages`. All three environments list **one required reviewer, the second GitHub account, with Prevent self-review on**.
- All three allow the branch `main` **and a tag pattern `v*`** (the policy list reads `main` as a branch and `v*` as a tag). There are two branch rulesets on `main` (pull request with code owners; required checks, no force push, no deletion) and **no tag ruleset**.
- Every merge to `main` is made by the maintainer account, so a run started by that merge was started by that account and it cannot approve it; the reviewer is a different account, so the owner can approve as that account and nothing blocks it. (No self-review deadlock.)
- **Builder lanes run as the maintainer account**, which can push branches and tags and, as an administrator, bypassed the review rule on the merges made with `--admin`. A workflow can be started by hand (`feed.yml` has `workflow_dispatch`), and a workflow that names an environment that does not exist **creates it with no reviewer and no branch rule**.
- `feed.yml` re-signs the Feeds every Monday at 06:17 UTC; the Feed expires after 14 days, so a fortnight without a tap would let it expire and every machine would report that something holds updates back.

**What that means.** Without a human on `feed`, any lane could push a tag such as `v999` carrying an edited `feed.yml` and run it, and the job would reach the feed key unattended. Round 1's idea of removing the reviewer from `feed` is **withdrawn**. The human stays on the two environments that use a key, and the branch rule is made to match what it claims.

**The approver:** the owner, as the second account, per release. Options considered: the release App merges the release pull request so the maintainer account could approve (the App would need a bypass of the `main` ruleset: a token inside a workflow able to merge anything: no); Prevent self-review off with the maintainer account as reviewer (the account lanes run as could approve its own release: no); a third account (the same as the second with one more to guard: no).

**Settings, as the one-time setup (the owner or the Mac, with an administrator token; the plan does not change them itself):**

| Environment | Reviewer | Branches | Why |
| --- | --- | --- | --- |
| `release` | the second account, Prevent self-review | `main` only | the release key |
| `feed` | the second account, Prevent self-review | `main` only | the feed key (releases and the weekly re-sign) |
| `promote` (new) | the second account, Prevent self-review | `main` only | adds a Release to `stable` |
| `withdraw` (new) | the second account, Prevent self-review | `main` only | marks a Release withdrawn |
| `github-pages` | none | `main` only | it publishes documents that clients verify (a Feed's signature and number): the worst an attacker who reached it could do is withhold a Feed or replay one that has not expired |

- **Create `promote` and `withdraw` before the workflows that name them are merged**, with their reviewer and branch rule, never by first use.
- **Remove the tag pattern `v*` from every environment's branch rule**, and add a **tag ruleset on `v*`** that only the release App (and nobody else, administrators included) may create or move; Release Please creates `v*` tags with its App token.
- **A settings check, not only workflow tests.** `scripts/release/check-release-settings.sh` (read-only, uses `gh api`): for `release`, `feed`, `promote` and `withdraw` it requires a non-empty reviewer list, Prevent self-review true and the branch rule exactly `main`; it requires that `github-pages` allows `main` only; it requires the tag ruleset; and it lists every environment the repository's workflows name (read from the files) and fails on one that does not exist. Tested against a fake API. It runs before every release and weekly (the manager's Monday card), and its output is evidence in the run book.
- **Taps:** per release **two** (`release`, then `feed`) as the second account; every Monday **one** (`feed`) for the re-sign. The manager reminds the owner on Monday and again on Wednesday; the Feed has 14 days of margin, so one missed week is safe and two are not.

**Publication date for the seven days.** The manifest's `publishedAt` is the release commit's date (`scripts/release/check-signing-release.sh` requires it to equal the commit time, so a rebuild can be compared), and the Feed has no "on latest since" field. A release that waits for a tap would spend the wait. The promotion workflow therefore reads the GitHub release's `published_at` (set when `ship` publishes it, a moment before the Feed lists it) and requires that the `latest` Feed currently lists the version. The Feed format is not changed (every installed updater would have to understand a new field).

T-411 fixes it in its own pull request (tests that read the version; commit-traces admitting exactly the release App's identity). The first release cannot start until #99 is green on the merged tree, and C4-0, C4-1, C4-2 and C4-6 must be on `main` before #99 is merged so that 0.1.0 carries the settings commands and the owner-path checks.

## 3. C6: one machine at a time

**The rehearsal first (C6-0, 2 days, in parallel with C4).** The throwaway-machine harness (`e2e/update-vm`) installs a release on a clean machine. It does not yet start from a machine set up the way these three are (units running `apps/<service>/src/main.ts` from a release folder, wrappers in `~/.local/bin`, databases in place). A scenario that builds exactly that state and runs `morndo install` over it proves the adoption before a real machine is touched: units adopted, databases opened, lanes' processes kept, health green, the old release folder still on disk, **and the dead-man's switch below firing and restoring**.

**Order: control plane, build PC, third machine.** The 10-21 plan said the third machine first, as a canary. The updater's rule is that a node is never newer than its control plane (`skew()`, `node_ahead`; the Rollout starts with the control plane): a node installed at 0.1.0 under a control plane still on the old build would be newer than it, and the design has only tested the other direction. The hub restarts on the control plane in every order, so putting it first costs nothing extra; the rehearsal, the backup and the dead-man's switch are what make that safe. If the owner prefers a real canary first, run a ten-minute spike in the harness (a node at 0.1.0 joining a control plane on the old build) and go by its result.

**The first install has no probation.** `morndo install` runs health checks after it starts the services, but it has no earlier updater-managed Version to roll back to, and probation belongs to an Update. The first step on each machine is protected by four things instead: the rehearsal; a written backup with the exact restore commands; the old release folder kept on disk; and a **dead-man's switch**: before the install, the operator starts `systemd-run --user --unit=c6-deadman-<machine> --on-active=25min` on the backup's `restore.sh`, whose first line exits if the `ok` marker file exists. The operator creates the marker, and stops the timer, only after the checks below pass. If the operator is gone, the hub is dead or the checks cannot run, the machine puts itself back in 25 minutes.

**Per machine (about 45 minutes each, including the checks):**

1. **Before:** the machine runs the same build as the others (all three run `4a0274cf`); nothing else is releasing; for the control plane, tell the manager.
2. **Backup, written down:** the unit files and drop-ins (`~/.config/systemd/user/morndo-*.service*`), the wrappers (`~/.local/bin/morndo*`), and each database by SQLite's online backup, into `~/.local/share/morndo-backups/<date>-c6-<machine>/` with a `restore.sh` and a `ROLLBACK.md` of the same commands; **start the dead-man's switch**.
3. **Install:** download `install.sh` and its signature from the release, verify them with the real key line, then `sh install.sh --role control-plane|node --channel latest --signers <file>` (the owner's fleet writes `latest`; the default for everyone else stays `stable`). It verifies the Manifest, installs through the Feed, adopts the units, starts the services and runs its health checks.
4. **Checks after each machine:** `morndo update --status` shows updater-managed, `latest`, current 0.1.0; `morndo doctor` is clean; the fleet lists the machine `online` on the release's commit; the lanes of that machine are online; a long message (about 28,000 characters) sent to a scratch lane arrives and is answered; on the control plane also `/api/health` with the new commit and schema, **the app served (not 503), https ready, and the manager answering through the hub**. Then create the `ok` marker and stop the timer.
5. **Window, on the control plane only:** after C4-1, set the window to 03:30 to 05:00 local with C4-1's window command, and `morndo update --status` shows it. The stored window defaults to none, so without this step the control plane would apply an update at any hour; the updater also has no signal that the owner is at the screen (the attending check is always false in this version), so the window is the only thing keeping applies out of his working day. A window never blocks an update the owner asks for with `morndo update`.
6. **Rollback trigger:** the install exits non-zero, a health row is wrong after 5 minutes, the node does not rejoin in 3 minutes, or the manager cannot be reached through the hub. **Rollback:** run `restore.sh` (units and wrappers back, `systemctl --user daemon-reload`, restart; the units point at the release folder that is still on disk) and restore a database only if the old code refuses the new one (the migrations between the builds so far were additive and the old code understands the schema floor; the release notes list any that are not). Minutes. The updater's own `--rollback` is not the way back from the first install.
7. **Do not start the next machine** until the previous one has been healthy for 10 minutes.

**What the updater does on the control plane afterwards.** With mode `apply` it checks the `latest` Feed on its tick; a newer verified Release is staged and applied at a safe point (nothing in flight that a restart would break) **inside its window**, restarting fleet, hub and node in order, then judging health in probation, **now including the owner-path checks of C4-6**; a failed check rolls the control plane back by itself and halts the Rollout so the nodes never take it. The nodes apply after the control plane commits, once the 30-minute soak (design §7) and a random delay of up to 15 minutes have passed. The manager's pane lives in tmux and survives; what the owner sees is a gap of the length of the restarts. Measured today, a release moved all three units on the control plane in about 4 seconds of restarts and the hub took about 6 seconds more to finish its first look.

6. **C6** on the control plane, then the build PC, then the third machine (section 3), each with its backup, dead-man's switch and checks; the control plane's window set in step 5 of section 3.
7. **0.1.1**, a small real change through the same run (merge, two taps, wait): the control plane takes it in its window, the nodes follow after the soak, and `morndo update --status` on each machine shows 0.1.1. **That is the auto-update running.** If it should be proven in the daytime, the owner runs `morndo update` on the control plane by hand (a window never blocks that).
8. **Every Monday** the weekly re-sign waits for one **[tap]** (`feed`). **Promotion** (C4-3) after seven days from the release's publication: **[tap]** as the second account on the `promote` approval; the owner's machines are already on `latest`.

## 5. Risks and what this plan does not do

- **Never run live:** the feed and Pages jobs, Release Please's own release, `morndo install` against a real Feed, and adoption over a release-tool setup. C4-5 and C6-0 exist to run each once before it matters.
- **The `latest` channel has no verifier gate** while C5 is held: a release reaches the owner's machines after CI, the manual QA and two taps. That is the accepted trade of putting the owner's fleet on `latest`; a withdrawal only marks a release, it does not move machines already on it.
- **No automatic check that every pull request in a release was reviewed** while C5 is held; the owner's tap on the release is that check.
- **The feed key is protected by the second account's approval and the `main`-only rule.** A lane that can push to `main` (the maintainer account bypasses the review rule as an administrator) could run an edited workflow on `main`, but it would wait for the second account's approval at `feed`; the approval is what stands there.
- **Time:** the estimate assumes three lanes in parallel and no defect in the rehearsals; a defect found in C4-5 or C6-0 adds days, not hours.
- **The release tool** (used for the bootstrap) keeps releasing until C6 is done and stays unused after it.
