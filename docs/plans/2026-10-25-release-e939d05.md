**What this is.** One build, `e939d0556`, onto the three nodes, in the order cp, pc, srv01, with the same tool and the
same per-node route that moved them to `4a0274cf4` on 2026-10-23. It is a release of the running system, not the

- `morndo audit --help` works without a hub; `morndo update` gets the settings commands and `--to`; the fleet gets a
  second, narrower socket that stays closed until it is configured.

**What changes in data.** The hub database goes from schema 25 to 29 (four additive migrations). The old build,
`4a0274cf4`, opens a schema-29 database: checked (section 2.3). No other database changes.

**Rules that apply.** Your tap releases (main releases need it). The release verifier (G-9) is a proposal and is not
built, so it does not apply. The srv01 wrapper (G-10) is installed on srv01, but the tool's `all` command, the only

2026-10-23. G-10's rule still holds in the order: srv01 never runs ahead of cp.

**What I would not ship yet.** The signed `0.1.0` release (release PR #99): three of the one-time GitHub settings it
depends on are not in place (section 6.2). Nothing else on main needs holding back.

**Biggest risks.** (1) After the first briefs are filed, rolling the hub back to `4a0274cf4` breaks its task panel for
those tasks, so the rollback window is short and the answer after that is to roll forward. (2) Do not add
`workerSocket` to the fleet config until the release is settled: the old fleet refuses an unknown key. (3) The new
lane-watch event reason must be accepted by the manager's event consumer, which this repository cannot check.

**Your tap:**
1. **Release now:** cp, pc, then srv01, about 1.5 hours of attended work (section 3).
2. **Release without srv01:** cp and pc now, srv01 later. A node may lag its control plane; the cost is that tasks
   merged meanwhile stay "merged, not live" until srv01 also runs the commit.
3. **Hold:** nothing changes; the nodes stay on `4a0274cf4`.

A feature cannot be left out of one build. Releasing without, say, proof of work needs a revert merged to main first
(another tap) and a new commit with its own checks; I do not recommend it.

`4a0274cf4` stands at schema 25 (`hub_store`), floor 0. On its first start the new hub runs 26, 27, 28 and 29 in one

### 2.3 Rollback: does `4a0274cf4` start on a v29 database?

**Yes.** The floor stays 0 (no migration is `breaking`), and the runner opens a database that is ahead on additive
migrations and runs nothing. Checked, not only read: on scratch copies of both builds, a data directory was opened in
turn by the old build (25), the new build (29), the old build again and the new build again. All four opens
succeeded, `user_version` stayed 29 after the old build's open, the floor row stayed 0, and an agent token written by
each build was readable by the other. The check wrote no live data; the scratch trees and data are removed.

Consequences for the rollback, and what the tool does:
- `morndo-release rollback --node cp --run <run>` restores unit files and wrappers and restarts; it does **not**
  restore databases unless `--restore-db` is given. Do not add `--restore-db` for a schema reason: it is not needed
  and it would drop what was written since the switch.
- **A rollback of the hub is not free once a lane has filed a brief** (ADR-0035, Consequences). The old build's task
  panel has no case for the `briefed` and `proof_listed` record kinds and throws for any task whose record holds one;
  the board itself still loads. The release refreshes the lanes' board block with the brief instructions, so briefs
  start soon after the release. Treat the rollback window for the hub as the first hour or two; after that the
  answer to a hub problem is to roll forward (or to patch the old build with the same default the new one has).
- The refreshed board block in the standing instructions files is not restored by a rollback. The tool copies each
  original to the backup folder (`claude-md/`); put them back by hand if wanted.
- A usage notice or lane record written by the new hub stays in the tables; the old hub does not read them.

## 3. The release steps, by the repository's procedure

### 3.1 Two things called a release

1. **The node release** (this plan): `morndo-release`, a tool kept in the private tooling repository, moves a node's
   release folder, unit files and console wrappers to one commit of `main`, with a backup and a check after each
   restart. This is how `4a0274cf4` reached cp, pc and srv01 on 2026-10-23, per node and by hand (the plan for that
   run is the private repository's `docs/releases/2026-10-23-bootstrap.md`), and the node's own log of that run reads
   `RELEASED srv01 4a0274c (was bd1907f)`.
2. **The signed release** (`scripts/release/README.md`, `docs/release-settings.md`, the `release`, `feed`, `promote`
   and `withdraw` workflows): Release Please's pull request #99 (`0.1.0`) is open and mergeable. Merging it starts
   the Release workflow, which builds, asks for the `release` environment's approval to sign, publishes, then updates
   the `latest` feed; `stable` follows by the `promote` workflow after seven days. It produces files for machines that
   install with `install.sh`. The three nodes are checkout installs and take nothing from it. **It is not part of this
   release** (section 6.2).

### 3.2 Which of the owner's rules apply

- **Owner's tap:** yes. Morndo main merges and releases need it; this plan is the thing he taps.
- **G-9, the release verifier:** does not apply. It exists as a proposal (`docs/plans/2026-10-23-release-verifier.md`
  on the branch `docs/release-verifier-proposal`); there is no `apps/release-verifier` on main. Its gates are the
  signed release's `publish` and `promote` environments, which this plan does not use. If a verifier is built, it
  would apply to track 2 only.
- **G-10, the srv01 wrapper:** `morndo-release-step`, the one command a srv01 lane may run, is installed on srv01 as a
  root-owned copy with its single allow rule in the user's agent settings (read on srv01). It is used only by the tool's
  `all` command. `all` is blocked: on the tooling repository's main the repository slug the checks gate reads is
  overwritten by a folder name for the release folder (lines 29 and 178 to 179 of the script), so the gate refuses every
  sha; the fix is held in an open pull request there (#67, T-386). So `all` is not used, as on 2026-10-23. The
  wrapper's rule survives in the order: cp first, srv01 last, never ahead of cp.
- **Tool commit:** the tooling repository's `main` tip is `0fe5acd`, the same tool commit the 2026-10-23 run used;
  the release-live directory has no change since (read 2026-10-24). Pin it again by full sha at release time.

### 3.4 The steps

Set once, on the pc, and use the same run id for every node and command: `SHA` the full commit
`e939d0556b364b3a77fde72f2af20d5954434cf9`, `TOOLC` the tool commit pinned in 3.2, `RUN` as
`<date-time>-e939d05` (a run id ends in the first seven hex of the sha).

1. **Pre-flight (read-only).**
   - The four required checks are `completed success` on exactly `SHA`
     (`gh api repos/morndo/morndo/commits/$SHA/check-runs`, the names `ci`, `fleet`, `traces`, `gitleaks`).
   - `SHA` and `TOOLC` are on `origin/main` of their repositories (`git merge-base --is-ancestor`).
   - The fleet lists cp, pc and srv01 `online` on `4a0274cf…` (`GET /v1/nodes` on the fleet socket).
   - Disk and memory on cp, pc and srv01; at least 2 GB free on each.
   - The tool is taken from git, not from a working tree, into a private folder, and its hash is compared with the
     committed blob (as the 2026-10-23 run did).
   - Tell the manager the hub and fleet will blink.
2. **cp.** Copy the tool to cp over ssh, run `node $SHA --node cp --dry-run`, read it against the stop rule below, then
   `detach node $SHA --node cp --run-id $RUN --live`, and poll `runs/$RUN.result` until it reads `released 0 <backup>`.
   The build (`npm ci`, the web build) takes minutes; the restarts take seconds.
3. **cp checks** (section 4.1). Nothing new is set in the hub environment for this release
   (the two variables the last release set are read, not re-set).
4. **pc.** `node $SHA --node pc --dry-run`, then `detach node ... --live`, from a plain terminal. Only the node agent
   is restarted (hub and fleet are inactive on the pc and never touched).
5. **pc checks and probe** (section 4.2).
6. **srv01.** The Mac session, as the node's user: preconditions (cp on the commit and healthy; disk; toolchain;
   `systemd-run --user true`; both clones fetch). Write the tool from git, compare its hash, `node $SHA --node srv01
   --dry-run`, apply the stop rule, `detach node ... --live`, poll the result file. The release only edits morndo files;
   it does not touch k3s, containerd, kubectl or Tailscale, and the Mac must not either.
7. **srv01 checks and probe** (section 4.3).
8. **Whole system** (section 4.4).

**Stop rule for every dry run.** Stop, change nothing and ask if: `OLD` is not the node's current release folder or
`NEW` is not its sibling for `e939d05`; a `unit:` other than the node's own set (cp: fleet, hub, node; pc and srv01:
node only); a `file:` that is neither a `morndo-*` unit file or drop-in under the user's systemd directory nor a
`~/.local/bin/morndo*` wrapper; a `db:` that is not a `.db` file in the four fixed folders; a `board file:` that is not
one of the three known shapes; or any line naming k3s, containerd, kubectl, Tailscale or a path under `/etc`, `/var`,
`/usr` or `/opt`.

**Rollback triggers and commands** (per node, in reverse order: srv01, pc, cp): a result other than `released`; a node
not `online` on the commit three minutes after; a failed row in section 4; the manager unreachable through the hub five
minutes after cp. `detach rollback --node <name> --run $RUN --run-id $RUN-rb --live`, then read `runs/$RUN-rb.result`
(`rolled-back 0`). No `--restore-db` (section 2.3).

## 6. Risks and open questions

### 6.1 Risks

- **R1. First start of the new hub on the real database.** Migrations 26 to 29 are additive and tested on upgrade paths
  from 25 and from 27 (the repository's tests); the old build opens the result (2.3). Not run on the real database. The
  tool backs it up first. Hub and fleet unavailable for about a minute, as on 2026-10-23 (estimate, not measured).
- **R2. Rollback of the hub after briefs exist.** See 2.3. The window is short; after it, roll forward.
- **R3. The board block refresh is an edit that a rollback does not undo.** It affects only sessions started after the
  switch; originals are in the backup folder.
- **R4. `workerSocket` in the fleet config breaks a rollback.** The fleet at `4a0274cf4` refuses an unknown top-level
  key and will not start. Do F2 only after the release is settled, or remove the key before rolling the fleet back.
- **R5. The new lane event reason.** `stale` events may now carry `no_turn_end`, a closed enum value. The tooling
  repository's protocol on its `main` already lists it, but the manager's own event consumer is outside both
  repositories and could not be checked. Open question for the owner: does it accept the value? Between cp and the pc, the
  pc's old `morndo lanes events` would also reject such an event if one arrives in that gap.
- **R6. The hub now calls GitHub.** From cp's network, unauthenticated unless a token file is set (this repository is
  public, so its references read without one). Rate limits and outages are handled (a green row is kept for at most an
  hour, then unfetchable), but a quiet failure shows as `unfetchable` on a card, not as an error.
- **R7. New push notifications.** Usage notices push one count-only notification each; a noisy source could be chatty
  until it settles. They can be silenced per source by forgetting it.
- **R8. srv01 is a production cluster node.** `npm ci` and a native build run there. The step edits only morndo files.
  Run it when the node is quiet; stop if the load is high. Do not touch cluster components.
- **R9. `all` stays blocked.** The release is therefore per node and manual, with no cross-node undo; a late problem is
  rolled back by hand in reverse order.
- **R10. The Stop hook stays as it is until F1.** The 20-second kill of the current script (47 of 1,577 hooks over four
  days, measured by the lane that wrote #139) continues, and the new lane-watch will now flag those turns. That is the
  intended visibility, and it is also new noise.
- **R11. Tests.** CI is green on the exact commit. I did not re-run the test suites for this plan; the compatibility
  check in 2.3 is the only thing run.
- **R12. The two Dependabot check runs that failed on this commit** are not part of the required checks; there are
  open Dependabot pull requests (#152, #153) that are not in this range.
