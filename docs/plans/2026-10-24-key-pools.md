# Key pools: several API keys for one provider, served in rotation. Plan, revision 1

**Status:** design only; no product code in this change. **Date:** 2026-10-24.
**Request:** the owner wants prepaid API keys used round-robin until each is empty, opt in, with an adapter layer so consumers get a key the way they do today, and domain rules applied.
**Builds on:** ADR-0018 (Connections, the lease gate, `apiKeyHelper`, the sealed store), ADR-0022 (the store and the Use gate are shared; Secrets stay a separate context), ADR-0029 (the account pool: the sibling for subscriptions).
**Code references** are to `origin/main` at `1494c11d`, read on 2026-10-24. External facts are cited with URL and the date read (all 2026-10-24).

---

## Owner summary (one page)

**What it is.** A *key pool* groups two or more of your existing API-key Connections (same vendor and runtime) behind one name. Asked for a key, the pool hands out the next member that can still serve, in a fixed order that survives restarts. A member that the provider refuses for lack of credit is marked *exhausted*, skipped, shown to you, and probed again once a day with a one-token call in case you topped it up. Nothing changes for a single key: it stays a Connection and a pool of one behaves as today.

**Why it fits.** A pool member *is* a Connection, so the lease gate (terms, budget, expiry, repo list, isolation) still runs on every key. The pool only decides *which* Connection a request goes to, and it holds no secret: it holds Connection names and health.

**What no API can tell us.** Nothing reports a key's balance (your premise; I found no balance endpoint in the pages I read, and did not search for one). So "until empty" means: use a key, learn it is empty from the first refusal, skip it from then on. One request per exhausted key is wasted, never more, and a daily probe costs a fraction of a cent.

**The one hard limit (read this).** Claude Code asks `apiKeyHelper` for a key, caches the answer five minutes by default, and re-asks only after a 401 or 403 ([settings reference](https://code.claude.com/docs/en/settings-reference.md), read 2026-10-24). A "credit balance too low" refusal is not a 401 or 403, so a session whose cached key just ran dry keeps failing until the cache expires or something reports the key. Rotation through the helper is therefore **per helper call** (per session, per cache lifetime), not per request, and the empty key must be reported back. Section 3.3 gives the report-back paths (the `run` wrapper, a `StopFailure` hook, the probes); a local gateway that sees every response is the clean fix and is deferred (as ADR-0018 deferred it).

**Cost (lane-days, one lane):** 9 days in four slices (section 8). **Slice 1 alone (domain, store, CLI, `lease --pool`) is 4 days** and already gives you rotation with manual and wrapper-reported exhaustion.

**Decisions for you (recommended answer first)** are in section 9. The three that matter: `round-robin` as the default mode (with `drain` as the "until empty" option); which report-back paths to build first; and whether you accept the terms line (I have not read Anthropic's terms on several accounts; section 7).

## 1. Domain model

### 1.1 Where it lives

A new aggregate **KeyPool** inside the **Connections** context, in `packages/domain/src/key-pool.ts` (pure, the clock is the `now` argument, as `pool.ts` and `connections.ts`). Not a new context: its members are Connections and the gate that serves them is CN8. Not inside `Connection`: a Connection must not know about its siblings (CN15), and a pool needs its own consistency boundary (the cursor).

**Naming.** `docs/domain.md` already has **Pool** (ADR-0029): the *subscription* accounts of a runtime, with Members, Marks and Seats. The new thing is the **Key pool**, always written with "key" in prose and `KeyPool` / `KeyMember` in code, so a grep never mixes them. They share nothing but the idea of rotation, and their rules differ (a seat has windows and resets; a key has a balance nobody can read). The two pools are never merged: a key is never a Pool member (PL1), a subscription is never a Key member (KP2).

### 1.2 Value objects

| Value object | Shape | Notes |
|---|---|---|
| `CredentialRef` | the **name of a Connection** (matches `CONNECTION_NAME`) | An opaque handle. Not the vault ref (`s-…`), not the fingerprint, never bytes. CN1 and CN5 hold for the pool by construction: it has no field a secret could travel in. |
| `RotationPolicy` | `{ mode: "round-robin" \| "drain", recheckEveryMs, coolMaxMs }` | `round-robin`: each request goes to the next servable member after the cursor. `drain` (the owner's "until empty"): stay on the current member while it is servable, move on only when it is not. Both skip exhausted members. Defaults: `round-robin`, 24 h, 1 h. Bounds: `recheckEveryMs` 1 h to 7 d. |
| `KeyHealth` | `{ state: "active" } \| { state: "exhausted", since, reason, nextCheck } \| { state: "failing", since, reason, until \| null }` | `reason` is a domain word: exhausted ∈ `credit`, `spend-limit`; failing ∈ `rejected` (the provider says the key is bad: revoked, expired, malformed), `denied`, `rate-limited`, `unreachable`. No provider text, no status code. |
| `Outcome` | `ok \| exhausted(reason) \| rejected \| denied \| rate-limited(retryAfterMs \| null) \| unknown` | What a *Provider adapter* returns (section 3.1); the only provider-shaped thing that crosses into the domain, already translated. `unknown` (a 5xx, an overload, a timeout, a malformed request) changes nothing: a provider outage is not a key problem. |
| `Servable` | derived: member active, or failing with `until` passed, and its Connection available | See KP3. |

### 1.3 Aggregate

**KeyPool** (one per name; the name shares the Connection namespace, KP1):

```
KeyPool {
  name, runtime, vendor,                 // fixed at creation (KP2)
  policy: RotationPolicy,
  members: KeyMember[],                  // ordered; the order is the ring
  cursor: CredentialRef | null,          // the member served last
  emptyNoticed: boolean,                 // PoolEmpty raised and not yet cleared
  events: KeyPoolEvent[], seq             // as the other aggregates
}
KeyMember { credential: CredentialRef, joined: number, health: KeyHealth }
```

Persisted as one JSON body with a version, saved only on the version it was read at (the `PoolStore` pattern, `apps/connections/src/adapters/pool-store-sqlite.ts`).

### 1.4 Invariants

| # | Invariant |
|---|---|
| KP1 | A pool name matches `[a-z][a-z0-9-]*` and is unique across pools **and** Connections, revoked ones included, and is never reused. `--connection` and `--pool` can therefore never name the same thing. |
| KP2 | A pool has one vendor and one runtime. A member is a Connection of kind `api-key`, custody `morndo`, status not `revoked`, with that vendor and runtime. A Connection is in at most one key pool. A subscription, an engine-layer Connection, or a key of another vendor is refused at join. |
| KP3 | **A member is never served while exhausted.** `pick` considers only servable members: active, or failing whose `until` has passed. A failing member with `until = null` (`rejected`) is not servable until the owner acts. |
| KP4 | **Rotation order is deterministic and survives restarts.** The order is the member list (join order). `round-robin`: the pick is the first servable member after `cursor` in ring order, wrapping; with no cursor, the first. `drain`: `cursor` while it is servable, else the next servable after it. The cursor is part of the aggregate and is saved before the pick is returned. Same state in, same pick out; no randomness, no clock in the choice. |
| KP5 | A pick that finds no servable member returns *PoolEmpty* (with the earliest time any member could return, if any) and serves nothing. It never falls back to an exhausted member. |
| KP6 | An outcome carries `observedAt`. One older than the member's current health `since` changes nothing, so a request that started before the key was marked cannot undo the mark. |
| KP7 | `exhausted` is left only by `ok` (a probe or a consumer report; KeyRecovered) or by the owner's `revive` (which only makes the member servable again; the first refusal re-exhausts it, so a wrong `revive` costs one request). `failing` with `until` is left by time or by `ok`; `rejected` only by `ok` after the owner rotated the key (ConnectionRotated) or by `revive`. |
| KP8 | Health is per pool member, not per Connection. Removing a member discards its health. Revoking a Connection ends its membership in the same step (a revoked key is never served by CN14 anyway; the pool must not keep naming it). |
| KP9 | A pool grants nothing and gates nothing (CN15). The lease gate (CN8) runs on the member the pick names; if it refuses (`off`, `terms`, `expired`, `repo`, `isolation`, `budget`), the service tries the next servable member. Gate refusals do **not** change health: a member over its Morndo budget is not "exhausted", it is declined. |
| KP10 | Narrowing is anyone's: removing a member, switching a member off (CN14), or setting `drain`. Widening is the principal's, judged by effect: creating a pool, adding a member (it may now serve), `revive`, raising `recheckEveryMs`'s bound, and acknowledging the pool's terms line. |
| KP11 | `PoolEmpty` is raised once on the transition to empty and not again until a member is servable again; `KeyExhausted` once per transition into exhausted (a repeat refusal for the same `since` raises nothing). |
| KP12 | Events carry names, reason words, times and the command id. They never carry the key, a fingerprint, a vault ref, a provider message, a status code, a header or a request id. |
| KP13 | Opt-in per provider. Nothing creates a pool by itself; a Connection with no pool is served by `lease --connection` exactly as today. A pool of one member serves that member and is, for every output, the single Connection's behaviour plus health. |
| KP14 | The order of members may be changed only by the principal (`pool move`), because it changes which key is spent first. Changing it does not move the cursor's member. |

### 1.5 Domain events

`KeyPoolCreated`, `KeyPoolRemoved`, `MemberJoined`, `MemberLeft`, `PolicyChanged`, `MemberPicked` (pool, member, at; written with the cursor, before the lease), `KeyExhausted` (member, reason, at), `KeyFailed` (member, reason, until), `KeyRecovered` (member, how: `probe` \| `report` \| `revive`), `PoolEmpty` (pool, backAt), `PoolRefilled`, `RecheckDue`, `TermsAcknowledged` reused from Connections for the pool's terms line (revision in the catalog). Widening events carry the command id (as CN13).

`LeaseGranted`, `KeyServed`, `LeaseClosed` stay Connection events and are unchanged: the audit of a served key is the Connection's, the audit of *why that key* is the pool's `MemberPicked`.

## 2. Application services and ports

New file `apps/connections/src/application/key-pool-service.ts`, the same shape as `PoolService` (load, apply one domain function, save on the version read, up to 8 retries). It imports only the domain, the protocol and its siblings (the architecture test in `apps/connections/test/architecture.test.ts` enforces that, and `no-vendor-names.test.ts` forbids any preset id or label in it).

| Service call | Does |
|---|---|
| `create(name, runtime, members, policy)` | KP1, KP2; the principal's command; terms line acknowledged. |
| `join / leave / move / setPolicy / revive` | The commands of section 3.4, with KP10 checks. |
| **`lease(pool, request)`** → `{ member, leaseId }` or a refusal | Pick (KP4, cursor saved, `MemberPicked`), then `LeaseService.lease(member, request)`. On a gate refusal (KP9) pick the next servable member, at most `members.length` times. On PoolEmpty: if a member is due for recheck, run **one** inline probe (bounded to 5 s) and pick again; else refuse with the earliest `backAt`. Exit 75 for a gate refusal as today; a new exit word `pool_empty` also exits 75 (the engine layer treats 75 as billing: it takes the provider out until later, which is right). |
| **`report(pool \| member, outcome, observedAt)`** | Applies KP6 and KP7; raises the Alerts (below). The one door every consumer uses. |
| `recheck(now)` | For each member with `nextCheck <= now` (exhausted) or a passed `until` (failing): ask the `ProviderProbe`, then `report` the answer. At most one probe per member per call. |
| `state(pool)` | Members in ring order with health, reason word, since, nextCheck, last pick; no ref, no fingerprint. Feeds the CLI and the page. |
| `onRevoked(connection)` | Removes the member (KP8); called by `ConnectionsService.revoke` in the same retry loop. |

**Alerts** use the existing `AlertSink` (`ports.ts`): `{kind: "key-exhausted" \| "pool-empty" \| "key-rejected", name, detail}`; `detail` is a reason word. `page.ts` already maps kinds to words; three words are added to `CONNECTION_WORDS`.

**Ports** (all in `application/ports.ts`; no port returns a secret):

```ts
type KeyPoolStore = {                       // the PoolStore pattern: one row per pool, JSON body, version
  load(name: string): { pool: KeyPool; version: number };
  names(): readonly string[];
  save(pool: KeyPool, version: number): boolean;   // false when `version` is no longer current
};
type ProviderProbe = {                      // adapter-side; it opens the vault itself, the application never sees bytes
  probe(member: { connection: string; vendor: string }): Promise<Outcome>;
};
type OutcomeClassifier = {                  // the anti-corruption layer; one per provider dialect, picked by catalog data
  classify(signal: ProviderSignal): Outcome;
};
type ProviderSignal = { status: number | null; kind: string | null; text: string | null; retryAfterSeconds: number | null; code: string | null };
```

The **Clock** and **SecretVault** ports exist (`Clock`, `SecretVault`); the pool adds no new vault port. `SecretVault.has/fingerprint/remove` are what the services use; the *adapters* that send the probe and serve the key open the secret, exactly as `leaseKey` does (`home.open(connection.ref)` in `compose.ts`, the plaintext type confined to the fixed importer list).

**Which classifier a pool uses** is data: the catalog preset gains an `errorDialect` field (`"anthropic"` for the first-party preset and the compatible ones that mimic its errors, to be confirmed per preset), next to the existing `dialect`. The application asks `classifiers.for(dialect)`; no vendor word appears in it.

## 3. Adapters

### 3.1 Provider adapter (Anthropic first): classify and probe

`apps/connections/src/adapters/outcome-anthropic.ts`. **What the docs say** (all read 2026-10-24):

| Signal | Source | Domain outcome |
|---|---|---|
| 2xx | | `ok` |
| 401 `authentication_error`: "an issue with your API key (for example, it's malformed, revoked, or expired)" | [errors](https://platform.claude.com/docs/en/api/errors) | `rejected` (needs the owner) |
| 403 `permission_error`: "does not have permission to use the specified resource" | same | `denied` (failing, rechecked) |
| 402 `billing_error`: "an issue with your billing or payment information" | same | `exhausted(credit)` |
| 400 `invalid_request_error` whose message says the credit balance is too low | the message string is documented: "Your credit balance is too low to access the Anthropic API. Please go to Plans & Billing to upgrade or purchase credits." ([API credits](https://platform.claude.com/docs/en/about-claude/api-credits-for-subscribers)). **The page does not give the status or the error type.** The 400 and `invalid_request_error` are the owner's observation, not documented | `exhausted(credit)` |
| 400 whose message starts "You have reached your specified API usage limits" (or "…workspace API usage limits") | [rate limits](https://platform.claude.com/docs/en/api/rate-limits), "Setting your own spend limit" | `exhausted(spend-limit)` |
| 429 `rate_limit_error` with `error.details.error_code` = `enforced_spend_limit_reached`, no `retry-after` | same, "Reaching your spend cap" | `exhausted(spend-limit)` (the message says when access resumes) |
| 429 `rate_limit_error` otherwise | same | `rate-limited(retry-after)`; without the header, 60 s |
| any other 400 | | `unknown`. **A malformed request must never exhaust a key.** Only the message match above counts. |
| 5xx, 529 `overloaded_error`, 504, a network error | | `unknown` |

Rules for the classifier:
1. Match on the **message text** for the two 400 cases, case-insensitively, tolerant of the status being 400 or 402, and treat it as a versioned table in the adapter. The docs say the `type` values "may expand", so the classifier is fixture-driven (section 8) and an unmatched 4xx raises an Alert `unclassified` carrying the status and error type only (never the text), so a changed message is noticed on the first occurrence.
2. A 429 for lack of *rate* cools the **key's organization**, which is what is wanted: several keys of separate accounts have separate limits; keys of one organization share them (the docs say limits are organization-level), so two keys of one org gain nothing against 429. The page says so at join if two members' organization ids are known (an `anthropic-organization-id` response header is documented in the errors page; the pool may record it as an opaque id to warn, never to route).

**Probe.** One `POST /v1/messages` to the preset's smallest listed model (the existing `smallModel` helper picks it), `max_tokens: 1`, one short user message. Cost: about 10 input tokens and 1 output token on the cheapest model; the catalog prices (dated) give the figure per probe and the page shows the day's total. Recorded as a Connection `SpendRecorded` estimate so budgets stay honest. **Not used as probes, because I could not confirm from the docs that they check credit:** `GET /v1/models` and the token-counting endpoint. Spike S1 (section 8) asks the owner to try both against one known-empty key at the machine, which costs nothing; if either fails with the credit refusal, probes become free.

### 3.2 Consumer adapter A: Claude Code `apiKeyHelper` (the existing lease path)

`morndo-keys lease --pool <name> [--lane L] [--workspace D] [--isolation …]` is `lease --connection` with one step in front: `KeyPoolService.lease` picks the member, then the existing `leaseKey` body runs unchanged for that member (caller proof, isolation, `KeyServed`, close). The helper line the launcher writes changes by one word (`--connection x` → `--pool y`); a single Connection keeps `--connection`. `--pool` and `--connection` are exclusive; `run --connection` gets the same `--pool` (a `run` is one lease on a picked member).

What the docs fix about timing ([settings reference](https://code.claude.com/docs/en/settings-reference.md), `apiKeyHelper`, read 2026-10-24): the command's output is sent as `X-Api-Key` and `Authorization: Bearer`; it is cached for five minutes by default (`CLAUDE_CODE_API_KEY_HELPER_TTL_MS`); it is re-run on a 401 or 403 and, from v2.1.246, when a cached JWT has expired. [Authentication](https://code.claude.com/docs/en/authentication.md): a failing helper makes requests fail "within three attempts"; a helper over 10 s shows a slow notice. ADR-0018 already sets the refresh to 60 s for our helper. Consequences, stated plainly:

- A pick happens once per helper call. With 60 s refresh, a long session moves across keys every minute or so; a short session stays on one. That is round-robin *over time*, not per request.
- A 400/402 credit refusal does not re-run the helper (only 401/403 do). The session keeps its cached key and fails until the refresh. Hence 3.3.
- Our pick is cheap (a SQLite write). Claude Code shows a slow-helper notice after 10 s; the inline recheck probe on PoolEmpty is capped at 5 s to stay well inside it.

### 3.3 How an exhausted key gets reported back

Three paths, cheapest first; each ends in `KeyPoolService.report`:

1. **The `run` wrapper (build first).** `morndo-keys run` already supervises the child and closes the lease with its outcome. It adds a classifier pass over the child's final failure (headless `-p` prints the API error) and reports `exhausted` / `rejected` for the member it leased; then, for a headless turn, it retries **once** on the next member (as `pool exec` continues a usage-limited turn on the next seat, PL8). This covers engine-layer lanes, which run through `run`.
2. **A `StopFailure` hook for interactive sessions.** Claude Code has a `StopFailure` hook "when the turn ends due to an API error", with matcher values including `billing_error`, `authentication_failed`, `rate_limit` ([hooks reference](https://code.claude.com/docs/en/hooks.md), read 2026-10-24); its output and exit code are ignored. The launcher's `--settings` adds `StopFailure` → `morndo-keys pool report --from-hook --pool <name> --member <name>`, where the member is the one this holder was last served (looked up by holder in the lease record, not passed as a secret). **Not confirmed:** the hook's input field names, and whether the credit refusal arrives as `billing_error` or `invalid_request`. Spike S2 reads the hook's input schema and records a fixture; until then the hook reports `unknown` for an unmatched type and does nothing else.
3. **The probes (always on).** The daily recheck, and the inline probe when the pool is empty. They also catch a key that ran dry while nobody ran a lane.

Anything else (a server that reads one key, 3.5) calls `pool report` itself.

A deferred fourth path, the **local gateway**, sees every response and reports exactly, and would give true per-request rotation. ADR-0018 deferred it ("isolates only when it runs as another user, and it adds a proxy to every request"); a key pool is the first feature that would benefit from it. Not in this plan.

### 3.4 Hub / CLI surface (the owner's opt-in)

`morndo-keys pool …` already means the *account* pool (`apps/connections/src/pool-cli.ts`). To avoid two meanings, the new commands are **`morndo-keys keypool …`**:

```
keypool create <name> --vendor V --runtime R [--mode round-robin|drain] [--recheck 24h] <key-connection>...   # principal; shows the terms line
keypool add <name> <connection>        keypool remove <name> <connection>     keypool move <name> <connection> --to N
keypool policy <name> [--mode …] [--recheck …]
keypool list                           # name, mode, members in ring order, health, reason, since, next check, last pick
keypool show <name>                    # one pool with its recent events (no secrets)
keypool report <name> --member M --outcome exhausted|rejected|rate-limited|ok [--from-hook]
keypool recheck [<name>] [--member M]  # probes the members due; --member probes now
keypool revive <name> <connection>     # principal
keypool delete <name>                  # members stay, as plain Connections
```

Exit codes follow the file (0 done, 1 refused with the reason on stderr, 75 gate refusal). `list` and `show` print JSON lines like `list` for Connections. Opt-in is `create`; there is no auto-grouping of keys that happen to share a vendor. The command words go into the one table in `packages/protocol` (ADR-0018 §1), and `create`, `add`, `revive` need the principal's command id (KP10).

The hub does not run these. It reads state through the same call path as the connections page (`apps/hub/src/adapters/connections-cli.ts`, `execFile` of the node program): `keypool list` is added to the page's read; narrowing commands (`remove`, `policy drain`) may be offered later through the existing `narrow` command kind; `create`/`add`/`revive` stay at the machine, since they widen.

### 3.5 Consumer adapter B: a server that reads one key from a `.env`

For a server that cannot call a helper (an extraction service that reads `ANTHROPIC_API_KEY` from its `.env`, called `extractor` below): `morndo-keys keypool write-env <name> --file <path> --var ANTHROPIC_API_KEY [--holder extractor]`.

- It picks a member (a `MemberPicked` event, a probe-less lease held for the file's life, holder `extractor`), and writes the value to `<path>` as `VAR=value` through a temp file in the same directory, mode 0600, then `rename`, so a reader never sees a half-written file. The path must be a file the node's Use gate allows (ADR-0022 `file` mode: a 0600 file; ADR-0018: a key is never put in a lane's environment). It refuses a path in a git work tree, a world-readable directory, or the vault.
- The server picks up the new value on its own restart or reload; the writer does **not** signal it (no process control).
- `write-env` runs as a rotation job: `keypool write-env --if-due` rewrites the file when the served member is no longer servable (exhausted, rejected), or when the rotation interval has passed (`--rotate-every 6h`, `round-robin` only). Run it from a user timer or by the server's own pre-start.
- **Report-back for this consumer:** the server (or a wrapper around its start) calls `morndo-keys keypool report <name> --member <m> --outcome exhausted` when it sees the credit refusal; the member name is in a sidecar `<path>.member` (the name only). A log-watching variant (`keypool watch --log <file>`, matching the classifier's message table, never copying the line anywhere) is the option when the server cannot be changed. Without either, the daily probe finds it within a day.
- The honest cost: the secret now sits in a file the server reads, which is what the owner has today. The pool adds the rotation, not the exposure; it shortens the life of any one value in that file.

### 3.6 The web card

One card on the existing **LLM connections** page (`apps/web/src/lib/connections/ConnectionsBoard.svelte`), read-only in v1: per pool, the mode, members in ring order, a health chip (active / exhausted / failing), the reason word, since, next check, last pick, and the day's probe cost. The page allowlist (`ConnectionsPage` in `packages/protocol/src/connections.ts`, a strict schema) gets a `pools` array of exactly those fields; **no ref, no fingerprint, no secret** (the existing page test asserts that, and gets the new rows). Actions stay at the machine in v1. A phone notification for `pool-empty` rides the existing alert path.

## 4. "Until empty" when the provider gives no balance

1. A member starts `active`. Nothing is read from the provider.
2. It serves until a refusal classified as `exhausted` arrives (3.3). `KeyExhausted` is raised, the Alert shows on the page and the phone, the cursor moves on. The cost is **one wasted request per exhausted key** (the refusal itself is not billed), plus whatever the cached helper value serves up to the refresh.
3. While every other member is servable, nothing else happens. When none is, `PoolEmpty` is raised once (KP11) and requests are refused with 75 and the earliest `backAt`, so the engine layer takes the provider out and falls to the next in the role's chain.
4. **Recheck.** `exhausted.nextCheck = since + recheckEveryMs` (24 h default); after a failed probe the interval doubles to a cap of 7 d. The timer is a user systemd unit on the node (`morndo-keys keypool recheck`), plus the inline probe when the pool is empty and a member is due. A successful probe returns `ok` → `KeyRecovered`, and the member rejoins the ring in its place.
5. `drain` mode is the same, with one difference: the cursor stays on a member until it is not servable, so keys are spent one after another, and the last one is spent last. `round-robin` spreads spend. Neither needs a balance.
6. The owner sees every transition: on the page, in `keypool list`, as Alerts, in the event log. A key he tops up is back within a day without a command, or at once with `keypool recheck --member`.
7. Morndo's own budget (CN8, CN10) is separate and optional: a member may carry a Budget as a *second* stop, a guard the owner sets from his own accounting; it declines the key (KP9), it does not mark it exhausted.

## 5. Security

- **Secrets stay in the store.** The pool's model, events, logs, Alerts, the page and the board hold names and reason words only (KP12, CN1, CN5). A test (section 8) serialises a pool with a planted key in a member's vault and asserts the key's bytes, its fingerprint and its vault ref appear nowhere in the pool JSON, its events, the CLI output, the alert file or the page message.
- **Leases stay per call.** `lease --pool` is one lease per call, `KeyServed` written before the key is printed, the lease closed after; the pool adds no long-lived lease. The caller proof, `--isolation`, the pinned `claude` binary and the signed-release check apply to the *picked member* unchanged (including a floor of `os`).
- **The pick is not a capability.** A caller cannot choose a member, only a pool; `lease --pool` refuses a `--member` flag. Only the principal's `create`/`add` decides who can be served.
- **Probes** open the key inside the adapter, send it only to the preset's base URL (the existing `baseUrlProblem` check and first-party-host rule apply), and never log the request or the response body; the classifier receives status, error type, a bounded message (256 chars) and `retry-after`, matches, and drops them. The probe's message string is never persisted.
- **A pool member's secret reaches a server consumer** only through `write-env` (3.5): a 0600 temp file renamed into place, in a directory the node permits, with the exact-value filter (SC6) covering the node's output paths. The writer refuses paths the vault or a repository owns, and never prints the value. The server's host is the owner's; the pool does not widen who can read the file beyond who can read it today.
- **Terms.** Rotating across several accounts can look like getting round a limit. The repo already puts a terms line in front of rotation for subscriptions (`TERMS_LINE` in `pool-cli.ts`, quoting the vendor's terms). For Anthropic keys I did **not** read the commercial terms or usage policy for this; the plan makes `keypool create` require an acknowledgement of a catalog terms line (revision in `vendors.json`, as CN4), and the line is written by the owner after he reads the sources the catalog already lists (`https://www.anthropic.com/legal/commercial-terms`). Prepaid, separate accounts rotated for *credit* are different from rotating to evade a *rate* limit, but that is the owner's reading to make, not mine.
- **Same-user processes are trusted** (the ADR-0018 limit). A process of the same user can read `connections.db` and see pool state; it still cannot read keys without the vault identity.

## 6. Migration

- **Single keys keep working untouched.** `lease --connection`, `run --connection`, the engine-layer providers, the Priority and the page all read Connections as before. A Connection that is in no pool is not different in any output.
- **A pool of one equals today.** `lease --pool solo` serves the one member; the only additions are `MemberPicked` and health. A test pins byte-identical stdout and the same `KeyServed`/`LeaseClosed` sequence.
- **Store.** One additive migration (4): table `key_pool (name TEXT PRIMARY KEY, version INTEGER, body TEXT)` in `connections.db`, marked `compat: "additive"` (`apps/connections/src/adapters/store-migrations.ts`; the schema-floor, downgrade-contract and migrations-additive tests cover it). A node on the previous release opens the database and ignores the table, as with the pool table (migration 3).
- **Routing.** A pool is addressed by `--pool`. The engine layer sees it as a provider named after the pool, with `bin: morndo-keys run --pool P --` and `probe: morndo-keys check --pool P` (the `gateBin` in `engines-sync.ts`). **Decision needed (Q5):** members listed in the Priority individually are replaced by the pool's one entry, so the chain does not try the same dry keys twice. Recommended: when a Connection joins a pool, its own engine-layer provider is turned off and the pool's provider takes its place in the order; leaving restores it. Both are structural changes, so they re-derive chains (ADR-0018 §4).
- **Existing keys.** Joining a key does not rotate it, re-seal it or change its fingerprint, budget or expiry.
- **Rollback.** `keypool delete` leaves the members as ordinary Connections and restores their providers; dropping the table is never needed.

## 9. Owner decisions, with recommended answers

1. **Default mode.** `round-robin` (spreads spend; skips dry keys), with `drain` as the opt-in "one key until empty, then the next". *Recommended: round-robin default, drain available.* Your words ("round robin … until each is empty") read as round-robin that drops a key when it is dry.
2. **Where it lives.** Inside Connections, as a new aggregate, commands under `keypool`. *Recommended: yes.* The alternative (a new context) splits the gate from its keys, the reason ADR-0018 rejected "keys as a context of their own".
3. **Report-back, in order.** `run` wrapper (with one retry on the next key) → probes → `StopFailure` hook → `write-env` report. *Recommended: build in that order; ship slice 1 first.*
4. **Gateway.** Defer the local gateway. *Recommended: defer, revisit once the report-back paths show how often the 400 reaches a session.*
5. **Priority entry.** A pool replaces its members in the Priority/chains (members' own providers go off while pooled). *Recommended: yes.*
6. **Recheck.** Daily, doubling to 7 days, one probe of at most a few tokens, plus the inline probe when the pool is empty. *Recommended: yes; my estimate, from the catalog's dated prices, is well under a cent a day for ten dry keys; slice 2 measures it.*
7. **Terms line.** `keypool create` shows a catalog terms line you write after reading Anthropic's terms, and requires your acknowledgement. *Recommended: yes; I did not read them.*
8. **Budget on a member.** Optional second stop from your own accounting (a Connection Budget). *Recommended: keep optional; no balance reading exists to make it automatic.*
9. **Server consumer.** `write-env` plus a report command, with the daily probe as the backstop. *Recommended: yes; the log-watch variant only if the server cannot call a command.*
10. **Web actions.** Read-only card in v1; all widening commands stay at the machine. *Recommended: yes.*
