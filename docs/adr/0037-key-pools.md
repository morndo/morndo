# ADR-0037: Key pools: several API keys of one provider behind one name, rotated only on exhausted credit

- **Status:** Accepted with the pull request that adds slice 1, 2026-10-25; amended by slice 2 (decisions 12 to 24) and slice 3 (decisions 25 to 30).
- **Builds on:** ADR-0018 (Connections, the lease gate, the sealed store, CN1, CN4, CN5, CN8, CN15), ADR-0022 (the store and the Use gate are shared; Secrets stay a separate context), ADR-0029 (the account pool, the sibling for subscriptions).
- **Rules:** KP1 to KP19 in `docs/domain.md` (KP16, the claimed probe, arrived with slice 3).
- **Plan:** `docs/plans/2026-10-24-key-pools.md`, revision 3.1, reviewed twice. This ADR records what slice 1 built and the decisions the plan left to the build.

## Context

1. The owner wants prepaid API keys used in rotation, opt in, with consumers getting a key the way they do today. A pool member is a Connection, so the lease gate still runs on every key.
2. No provider API reports a key's balance (plan section 4). "Until empty" means: use a key, learn it is empty from the first refusal, skip it from then on.
3. A refusal is not always a reason to move on. The Usage Policy forbids circumventing a ban with another account (plan section 7). Rotating on a 401, a 403 or an account on hold would move traffic to another account because one account was refused.
4. Provider facts (read 2026-10-25): the errors page lists 401 `authentication_error`, 402 `billing_error`, 403 `permission_error`, 429 `rate_limit_error`, and says a spend limit the owner set returns 400 `invalid_request_error`; the rate-limits page gives the monthly cap's 429 with `error.details.error_code` `enforced_spend_limit_reached` and no `retry-after`, and the spend-limit message "You have reached your specified API usage limits" with the date access resumes [S1, S2]. Which status a credit refusal carries is not documented; the classifier matches the message and accepts 400 or 402.

## Decision

1. **A KeyPool aggregate inside the Connections context** (`packages/domain/src/key-pool.ts`), not a new context and not a field of Connection: a Connection must not know its siblings (CN15), and a pool needs its own consistency boundary (the last pick, the member health, the terms). Pure; the clock is the `now` argument. A member is the Connection's **name**. The pool holds no ref, no fingerprint, no secret (CN1, CN5).
2. **Key pool, never "pool" alone; "last pick", not "cursor".** `docs/domain.md` already has Pool (ADR-0029, subscriptions). The two share the idea of rotation and nothing else, so prose says "key pool" and code says `KeyPool` / `KeyMember`. The plan called the saved position of the rotation the cursor; that word is a catalog preset id, which a repository test keeps out of the domain and application sources (`no-vendor-names`), so the term and the field are `lastPick`.
3. **Rotation: `round-robin` by default, `drain` as the opt-in "until empty"**, order = join order, deterministic, saved last pick (KP4). No randomness, no clock in the choice.
4. **Automatic rotation only on exhausted credit or an owner-set spend limit.** A 401, 403, `account_on_hold`, `authentication_failed` and the tier's monthly cap are `failing`: they **block the pool** (KP3) until the principal revives the member or the Connection is rotated to a new key. A probe never clears a failing member. A 429 for rate is recorded and changes nothing.
5. **The chosen member is saved as the last pick before the lease gate runs, the pick event after it** (KP9, KP15). Two concurrent picks then see each other's last pick and get different members in round-robin. A gate refusal (budget, terms, repo, isolation) tries the next servable member, records the refused words in the one `MemberPicked`, never changes health, and puts the pointer back (review F6): a refusal that is only one caller's does not move the pool for everyone, and in `drain` a caller given another member leaves the pointer where it was.
6. **A pool holds only keys of accounts the owner holds.** A join needs the member's provider organization to be one the principal confirmed, or `--confirm-own-account` (`OwnerConfirmed`, with the command id). Slice 1 has no probe, so it cannot read an organization id: **every member needs the flag in slice 1**, and the flag is the whole check.
7. **Terms: the principal acknowledges a catalog line at `keypool create`** (`--by <who>`, as CN4). The preset carries an optional `keyPool` object (`errorDialect`, `termsRevision`, `termsLine`); only the first-party preset has one, so no other provider can host a pool yet (`no_classifier`). A pool whose acknowledged revision is not the catalog's is refused by the gate word `terms`. The line's wording is the owner's to revise.
8. **The classifier is an anti-corruption adapter** (`adapters/outcome-anthropic.ts`), chosen by the preset's `errorDialect`. It turns a status, an error type, a bounded message, a `retry-after` and a date into an `Outcome` and drops them. An unmatched 4xx raises an `unclassified` alert carrying the status and error type only. A malformed request (a bad `max_tokens`) is `unknown` and never exhausts a key.
9. **Report-back in slice 1 is the `run` wrapper, and it reads only the agent CLI's structured result** (review F1). A failed headless run (`-p`, the launcher's own `--output-format json`) prints one JSON record; `is_error`, `api_error_status` and `terminal_reason: api_error` are the CLI's own fields, and only that record is classified. Free text is never read: the model's and the tools' words are in the output too, and a repository file or a page the model read could otherwise block or steer the pool. Output that is not that one record, a run whose caller chose another `--output-format`, and an interactive session are read as nothing. The wrapper retries once, on a different member (the refused one is skipped), only when the first attempt had done no work (cost 0, no model use, one turn); a run that had spent money or edited is reported and stopped, so it never pays or edits twice. Observed record shapes: PR 155; the `StopFailure` hook (slice 4) replaces the reading of the run's output.
10. **Storage: one additive migration (4), table `key_pool`**, one JSON body and a version per pool, saved only on the version read. A deleted pool leaves a tombstone row, so its name is never reused (KP1). Names are shared with Connections: a Connection cannot take a pool's name, nor a pool a Connection's.
10a. **Who may do what is enforced in the service** (review F2). Create, add, remove, move, policy, revive and delete are the principal's. A report is the principal's (exhausted, failing, limited; never ok), the machinery's (the run wrapper; an ok only from a real Messages answer), or a lane's: exhausted, failing or limited for the member of its own open lease, with the lease id, as the process that holds it or a child of it. **A lane holding a lease can therefore report its own member failing, which blocks the whole pool until the principal revives that member**: the price of letting a lane say its key was refused, and a denial a lane can already cause by holding the key. A command name that is only whitespace is no principal, in the domain and in the service. A `--by` that is missing, blank or the literal `true` (what a bare flag stores) is no name. The CLI cannot tell a lane that leaves `--lease` out from the principal at the machine: that is the same-user trust ADR-0018 states for every command of this bin (`revoke`, `budget`), and the sandbox, not this command, keeps a lane from it.
10b. **The key-pool terms are their own catalog file** (review F7): `packages/protocol/catalog/key-pools.json` beside `vendors.json`, read by `FileCatalog`. An older build's strict preset schema refuses an unknown field, and the helper (`lease`) runs whatever `morndo-keys` is installed with the catalog it is given, so a field in `vendors.json` would stop every key from being served on a node whose helper is older than its catalog. With the file apart, an older build never reads it, and no ship order is needed. A test pins `vendors.json` to the keys of the schema before key pools.
10c. **A resume date is capped at a year from now** and is taken only from the structured result (review F5); the alert's error type is cut to 64 characters.
11. **Revocation reaches the pool through a lifecycle hook** on `ConnectionsService` (`reserved`, `revoked`, `rotated`), and a pick heals a pool whose member was revoked behind its back.

12. **Slice 2: a pooled `run` holds a Grant, and its helper is `helper --pool <name> --grant <id>`** (plan 3.3). The plain `helper --lease <id>` serves the key of the one Connection its lease was taken on, so a pick made at launch would hold for the whole session. For a pooled run (claude runtime) the grant is opened in the same save as the pick, and each helper call (`handOff`) reads the grant, its lease in the directory and its member's health, and moves the run to the next member when the member is exhausted or its lease's refresh is refused by the gate (budget, expiry, off, terms). The new member is gated again (CN8 runs in full, a member over budget is passed over), the old lease closes with outcome `handoff` and the new one is granted in one directory save (`swapLease`), the grant is saved after it with the pick, and `KeyServed` is written before the key is printed. A failing member or a blocked pool prints nothing and says `pool_blocked`; a helper whose authority has ended says `authority` and takes no lease, so a hand-off is no way round the call cap (KP17). A refusal is a word on stderr and exit 1 (an apiKeyHelper treats every non-zero the same). Every pooled helper call writes one `KeyServed`; `helper --lease` of a single Connection still writes none and is unchanged.
13. **A crash between the two stores mends itself** (KP19), and a second process cannot add a lease while the first is re-leasing: a re-lease with no old lease to close is refused (`held`) in the same directory write if the holder already has a live lease on the pool, and the loser adopts it. The directory and the pool are two writes. The order is fixed (swap, then grant with the pick, then the audit line); a crash after the swap leaves a live lease the grant does not name, which the next call adopts; a crash after the grant save leaves a lease with no audit line and nothing printed, which the next call serves. Two calls at once are serialised by the directory's version; the loser adopts. Tests inject the crash at both points and assert one live lease and one `KeyServed` per printed key.
14. **Attribution after a hand-off is by session, with the window as the fallback** (KP18). The helper's cache is per process, so the key a refusal came from is the one its session was last served. The grant records, per session (the process-tree entry just below the holder, the same for a helper call and for a report made under that session), the member it was served; a report from a known session is that member's, exactly, so a new key that is already dry is marked at once and an old key still held by another session is blamed on the old member. A session the grant has not seen falls back to the plan's window: less than 60 s after a move the report belongs to the member the run came from. The time is the service's clock. A lane cannot choose which member it blames: it can only report about the key its own session holds, or, outside the record, about the member the window names, both members of its own grant (a lane can already report its own member failing, ADR decision 10a). The plan's claimed probe of the new member needs slice 3's probe and is not built. A report names its grant, never a member: `keypool report <pool> --grant <id> --outcome …`, by the grant's holder or a child of it, exhausted, failing or limited only. `--grant` with `--member` or `--lease` is refused (`usage`). A lane that holds a lease of a pooled run no longer knows the lease id, so the lane-report path of slice 1 now goes through the grant.
15. **The grant id is `g` plus its first lease's id.** Lease ids are `l<seq>` of the directory and never reused, so no random source enters the service. A grant is not a capability: who may use it is the process tree (the holder or a child), as for a lease.
16. **A pool is a routing name** (plan section 6, decision 6 of the plan). The Priority order and the role picks hold the pool's name in place of the members' (`foldPool`), the engine layer gets a provider named after the pool (`morndo-keys run --pool P --`, probe `morndo-keys check --pool P`) and the members' providers are registered off. Leaving, deleting the pool and revoking the last member re-derive through `unfoldPool` and give the members back. A page priority or role save that left a pool out keeps it (`withPools`), so the page cannot drop a pool it does not yet show (its rows are slice 5). A failed engine write after the pool is saved says `saved, engine layer not updated (retry: morndo-keys keypool sync)`; `keypool sync` is the idempotent retry. The re-derivation sits behind a port (`PoolRouting`), called after the pool's own save, so the aggregate holds no engine-layer knowledge.
17. **`check --pool P` asks whether some member could serve now and moves nothing.** It runs the same gate attempt as `check --connection` on each servable member in ring order and answers the first that passes; it saves no last pick and writes no `MemberPicked`, so a health probe by the engine layer does not turn the rotation. Exit 75 with `pool_empty`, `pool_blocked`, `terms` or the gate's word.
18. **A key reaches the agent only after the run's output filter holds it.** The run may be moved to any member, and a key the child prints after a hand-off must be redacted as the first one is. By construction: a pooled run listens on a private unix socket (`filter-channel.ts`: a directory 0700 under `$XDG_RUNTIME_DIR` or the temp directory, the socket 0600, one JSON line in, `ok`/`no` out; which keys it takes is decision 23), and its helper line is `helper --filter <socket> --pool P --grant G`. The helper opens the key it is about to print, **sends it to that socket and prints it only on `ok`**; the run adds it to both redactors before answering. No answer (socket gone, the run dead, a refused key, a timeout of 2 s) means no key: the helper exits 1 with `filter_unreachable`. Which socket the helper may use, and which keys the socket takes, are decisions 22 and 23. The filter's set therefore only grows for the run's life and depends on nothing that can change under it (not the pool, the directory or a cap on the grant's history). Cost: the key crosses one more same-user local channel (the trust of ADR-0018), the audit line is written before the hand-over, so a refused hand-over is an over-audit, never an under-audit (KP19's "no `KeyServed` for a key it did not print" holds in the safe direction only), and a launcher holds every key it has handed out, plus the start set (every member then in the pool), in memory.
    The store watch (`pool-keys.ts`) stays as a **fallback**, and is fail-closed in its own right: it re-reads on a version change and learns the keys of the grant's lent members and current members. Its required set only grows for the watch's life; a required name with no key Connection (gone, or not a key) or a required key that fails to open throws `FilterIncomplete` naming the member, never the key; keys that did open are carried. `guardedRelay` writes a chunk only after a read worked; on failure it writes one marker per stream per stretch, never the chunk, and after 30 s gives up once: the run is stopped as when its reader goes away (status 1, lease closed as failed) with one stderr line naming the member. A 150 ms poll keeps it current while nothing prints, and a poll that works ends a withheld stretch. `MORNDO_FILTER_WATCH=off` is a test seam that switches the watch and the poll off so only the channel is in play.
    *Path by path, why an unknown key cannot pass (pooled run, agent output to anything written):* (a) child stdout and (b) child stderr: only through the relay, whose filter holds every key the helper has handed out; the redactor's held-back tail is flushed only after the relay settled and never after a give-up. (c) The run's own error text (a spawn failure) is the launcher's or Node's text, not the agent's output. (d) The lease's close outcome is that error word or `done` or `failed`. (e) The give-up line holds member names. (f) Report-back: the classifier reads the agent CLI's structured result from the raw output, matches it and drops it (KP12); only an `unclassified` alert of a status and an error type cut to 64 characters is kept. (g) Cost is parsed as numbers. (h) The model id from the result goes into an engine mark only if it is shaped like a model id (`^[A-Za-z0-9][A-Za-z0-9._:/@[\]=,-]{0,99}$`) and holds no key the filter has. (i) The helper prints the key to its caller only; its stderr and exit are words; the audit lines, the grant and the pool events hold names, ids and times. (j) `keypool report --grant` run by the agent's tools prints words only. Non-pooled runs keep their synchronous filter of the one key.
19. **A member that leaves or is revoked does not strand its run.** The grants of runs on it stay; the next helper call swaps the run to another member (why `left`), closing the removed member's lease as for any hand-off, and a report credited to the member that left is accepted and changes nothing. With no member left the call says `pool_empty` and the run's end closes its lease.
20. **A hand-off books the old lease's reservation as spend, as every close without a cost does.** Nothing reads what a session has used while it runs (the agent CLI reports its cost when it exits, and the helper has no cost), so at a hand-off the old lease is closed with its reservation as the estimate (`--reserve`, default 5 USD) and the run's final cost goes to the last member. This over-counts, never under-counts: a capped member that was handed off from several times can be refused a later lease for `budget` until the principal reconciles its spend. Use a smaller `--reserve` for runs on small budgets. A reading of mid-run use would replace the estimate; none exists.
21. **Grants are swept like leases.** A run closes its grant at its end; `lease`, `run` and `check` also drop the grants whose holder process is gone.
22. **A helper call under a grant hands its key to that grant's own run filter, or prints nothing** (review rev-156f, finding 1). Decision 18's "no ack, no key" held only for the helper line the run wrote: the helper took `--filter` from its arguments, connected to any path and treated `--filter` as optional, and the agent's tool is a child of the run's holder, so the grant's authority admits it. A tool could run `helper --pool P --grant G` with no `--filter` (key printed, nothing sent to the run) or with `--filter` at a listener of its own that answers `ok`. Now the run records the path of its socket in the grant once, before its child starts (`bindFilter`: a second bind is refused, even to the same path, so no later caller can move it). `handOff` takes the caller's `--filter` and refuses with the word `filter` when it is missing, different, or the grant was never bound; this is checked after the holder check and before anything else, so a refused call takes no lease, writes no `KeyServed` and does not count against the helper's cap (KP17). Before it sends, the helper checks the socket (`filterSocketTrusted`): a real socket, not a symlink, owned by the caller's uid, mode 0600, in a directory it owns with mode 0700; otherwise it says `filter_untrusted` (the audit line is written already: an over-audit). **What this does not close:** a process of the same user that can write the run's 0700 directory can unlink the socket and bind its own at the same path with the same owner and mode, because Node gives a listener no proof of who answers (no peer credentials). That needs the same-user trust ADR-0018 states for every command of this bin and the sandbox, not this check, keeps an agent's tool out of the directory. The same holds one level up: `grant.filter` lives in `connections.db`, so a same-user process that can write the database can set it to its own listener (0600, in a 0700 directory) and `filterSocketTrusted` passes. Such a process can read the age identity and the vault files, which are same-user readable, so it could take the keys directly: the trust is ADR-0018's, and this check adds no boundary against it. What keeps a run's own tools off the database, the vault and the identity is the sandbox this launcher turns on for the run (`SANDBOX` in `runtime-claude.ts`: enabled, fail if unavailable, no unsandboxed retry) together with the run's deny list; a process outside that sandbox has the same-user trust.
23. **The filter channel takes only keys of the pool the run is on** (review rev-156f, finding 2). Any same-user process that found the socket could send keys: sixty-four junk keys filled the set, so the run's next real hand-off was answered `no` and the run lost its key; a one-character key was accepted and made the redactor over-redact all output. A key must now be 16 to 1024 characters and equal the key of a Connection that is a current member of the pool, the grant's member, or a member the grant lent the run (`acceptsPoolKey` reads the pool and the directory at the moment of the call and compares the opened key with the sent one; compared as whole keys, not by fingerprint: the store's keyed tag is 12 hex characters, and equality with a key the vault opens is the stronger test). A refusal, a throw or an unreadable store is `no` and adds nothing. With junk refused at the door the set's cap is only a memory bound, 1024 distinct keys, far above a pool and all its rotations. The channel can still be asked to re-send a real key, which changes nothing. Junk senders must not make the real helper's two seconds lapse (review rev-156g): a socket that has not finished a line within a second is cut loose (a sender writes its line at once, so a slow pool is not mistaken for a slow sender); at 32 open sockets the oldest one that has not finished a line makes room, and a new one is refused when all of them are waiting for the pool; the pool is asked about one key at a time (each check opens the run's home), with at most 8 waiting or running and the rest answered `no` at once. A same-user process that floods with distinct keys can still delay or deny the hand-off: it fails closed (no key is printed, `filter_unreachable`), and the same process could kill the run.
24. **A killed launcher's socket directory is swept, and a path too long for a socket says so** (review rev-156f, finding 3). The directory is named `mf-<pid>-<random>` after its owner. At the next start the launcher removes every such directory in the same root whose owner process is gone (`ESRCH`), that is a real directory owned by the same user, at least a minute old (a launcher may be between making it and listening), holding nothing but an optional `f.sock`, and on whose socket nobody answers (a connection that is refused, or no socket at all). The last test is what separates a dead launcher from a live one in another pid namespace (a container, `bwrap --unshare-pid`) that shares the directory: its pid is invisible here, but its socket answers, so its directory is kept (review rev-156g); a symlink, another name, an old-format name or a directory with other files is left alone, and a failed sweep never stops the run. A reused pid keeps a directory alive: it leaks, it never removes a live run's. A root that makes the socket path longer than the limit (107 bytes on Linux, 103 on macOS) fails closed before anything is created, with `the filter socket path is too long (N bytes, at most M): set XDG_RUNTIME_DIR or TMPDIR to a shorter directory`.
25. **A probe is one Messages request, made under the member's own gate** (plan 3.2, slice 3). `POST {base}/v1/messages` to the pool's probe model with `max_tokens: 1` and a one-character user message, five seconds at most. Headers: `x-api-key` (the docs call it the legacy fallback for `Authorization`, still supported), `anthropic-version: 2026-10-21` (the version the docs list first and recommend; no `temperature`, `top_p` or `top_k` is sent, the three it removed), `content-type`. Never the token counter and never the models endpoint: neither is evidence of credit (KP7), and a test reads the adapter's source for both names. A redirect is never followed (the key must not leave for another host), a success body is cancelled unread, an error body is read to eight kilobytes and reduced by the classifier to a signal (status, error type, 256 characters of message, retry-after, error code, resume date), and the key is redacted from that signal in case a provider or proxy echoes it. A timeout, a network failure, a bad base URL or a key that will not open is `unreachable`: no state change, no cost. A 404 `not_found_error`, or a 400 `invalid_request_error` that is not the credit or spend-limit phrase and names the model or the `anthropic-version`, is a **configuration error, not a verdict on the key** (`misconfigured`, word `model` or `version`): it raises one `probe-config` alert (once, however often it recurs), reports nothing, and leaves the member as it is. An unmatched 4xx raises its `unclassified` alert once per change: the member keeps a hash of the last detail alerted for each kind (`unclassified`, `probe-config`), not the detail (it holds a status code and the provider's error type, which the pool never keeps, KP12); the same detail is not raised again however many other alerts came between, a good answer clears it so the same detail is news again after a fix, and an unreachable provider is no change. The base URL is the preset runtime's, so a catalog entry is what points it at a stand-in in tests. Sources read 2026-10-25: https://platform.claude.com/docs/en/api/overview, https://platform.claude.com/docs/en/api/versioning, https://platform.claude.com/docs/en/models/overview (`claude-haiku-5-5`), https://platform.claude.com/docs/en/about-claude/pricing (Haiku 5.5: $0.10 per million input tokens, $0.50 per million output tokens up to 100,000 prompt tokens).
    **The probe model is data**, in a third catalog file `packages/protocol/catalog/key-pool-probes.json` (`vendor`, `model`), for the reason of decision 10b: an older build's strict schemas refuse a field they do not know, so the probe model does not go into `vendors.json` or `key-pools.json`, and a test pins both files to the fields an older build knows. **One probe costs** about ten input tokens and one output token: about $0.0000015 on that model. The recorded estimate is `KEY_PROBE_COST_USD`, $0.00002 (a margin that also covers Haiku 4.5, ten times dearer). The probe is made under a gated probe lease (role `probe`, reservation the estimate), closed with that cost, so it lands on the member's Connection and its budget; an `unreachable` probe closes at no cost. **A probe never runs against a real key in tests or QA**: a local server stands in for the API.
26. **A probe is claimed before it is made (KP16).** `claimProbe` sets the member's `probingUntil = now + 30 s` and its `nextCheck` in one saved write and writes `ProbeClaimed` (member, why: `due`, `manual` or `suspect`, time; names and words only). A caller that finds a claim in the future does not probe (`claimed`), a due claim on a member that is not due is `not_due`, on a member in the wrong state `state`. A claim is not a health change: `since` and `lastChange` stay, so an answer that left before a later change (a report, a revive) is older than it and changes nothing (KP6). The claim lapses by itself and is **kept after every answer** (a dry one, and an ok on a suspected member as well), so no probe path runs more than once per member in thirty seconds; recovery, a refused key and the owner's revive clear it. Every claim records its time (`lastProbe`); a `due` or `suspect` claim is also refused (`not_due`) within one recheck interval of the member's last probe, of whatever kind (and `dueMembers` does not list such a member), so repeated grant reports inside the hand-off window cause one probe, not one per report, a due probe cannot follow a manual one at once, and a suspect probe that finds a key dry under a past resume date is not followed by a due probe thirty seconds later (rev-158, rev-158b). A manual claim is the principal's and is held by the claim alone. A claim whose probe never started because the member's own gate refused is **released at once** (`ProbeReleased`, `nextCheck` and `lastProbe` restored), so a declined probe does not skip the interval; a process that dies after the claim is not mended, the claim lapses and the interval stays skipped. N callers hitting an empty pool cause one probe: the losers find the claim and refuse with `pool_empty`.
27. **When a member is checked again, and `resumeAt`.** An exhausted member's `nextCheck` is the time it ran dry plus the pool's recheck interval (24 h by default, at least 1 h), or the date a refusal named (capped at a year). The claim moves it on by the current interval at once. Only a `due` probe moves the schedule: one that finds the key dry again counts a failed probe and doubles the interval each time, up to seven days, unless the refusal named a date, which wins; a manual or suspect probe never moves `nextCheck` or counts a failed probe (eight manual probes used to push the next check a week out, rev-158). A resume date that is not in the future (`resumeAt <= now`) is no date: the member is due after the interval, not at once. It raises nothing (KP11: one `KeyExhausted` per transition). A Messages ok recovers (`KeyRecovered` by `probe`, failed probes back to 0); a probe that finds the key refused makes it `failing` (the pool blocks, KP3); a rate limit or an unclassified answer changes nothing, and an unmatched 4xx raises one `unclassified` alert of status and error type only. The probe's answer is observed at the instant of its claim.
28. **Who probes.** `morndo-keys keypool recheck [<pool>] [--member M]` probes every due member of the pool (every pool without a name); `--member` probes that member now, through the same claim; `recheck` is the principal's, like `revive` (`recheckBy`: an operator is refused with `principal`); the inline probe and the suspect probe are the machinery's. It prints one JSON line per probe, `{"pool","member","outcome"[,"word"]}`, outcomes `recovered`, `healthy`, `exhausted`, `failing`, `limited`, `unknown`, `unreachable`, `misconfigured`, `declined` (the member's gate refused: `off`, `terms`, `budget`, `repo`, `isolation`; nothing was sent) and `skipped` (`claimed`, `not_due`, `state`, `missing`, `no_probe_model`). An hourly user timer, `apps/connections/units/morndo-keys-recheck.{service,timer}` (`OnCalendar=hourly` with up to five minutes of spread and `Persistent=true`, which only has an effect on a calendar timer: systemd.timer(5)), runs it; `systemctl --user enable --now morndo-keys-recheck.timer` installs it, and the updater's install list is **not** changed in this slice. An empty pool with a member due also probes inline, once, before `lease --pool` and `run --pool` pick again; `check --pool` never probes (a health check moves and spends nothing). **How often:** at most once per due member per interval (an hour at the finest), at most one claim per member in thirty seconds by any path; a manual probe is the principal's explicit act and is limited by that claim alone, so it can run right after a timed probe (the plan's "per interval for whatever path" would have made it useless for topping up a key).
29. **KP18's claimed probe, left open by decision 14.** A report that falls back to the hand-off window (a session the grant never served) is credited to the old member and now also names the grant's current member as the one to suspect, when the report is a credit refusal. `reportByGrant` returns it; `keypool report --grant` probes that member with why `suspect` (a probe of an active member sets no `nextCheck`). A dry new key is marked exhausted at once, once; a healthy one answers `healthy` and is left alone and the claim cleared.
30. **What a probe cannot do.** It goes through the member's own lease gate, so a member with a repo allow-list or an `os` isolation floor is `declined` from the timer's workspace (the default first-party preset is `rules`); a declined probe has still moved `nextCheck`. It does not read the organization id from the response headers (the ownership check stays the owner's confirmation, decision 6). It does not make a key whose account holds a payment problem look healthy: only a Messages answer recovers (KP7).

31. **The failure hook reads the text for every code that can be a refusal of the key** (slice 4, spike S2, 2026-10-26). Real agent CLI 2.1.310, a local stand-in for the Messages API, a synthetic key: the `StopFailure` hook fires in `-p`, its stdin has `session_id`, `transcript_path`, `cwd`, `prompt_id`, `effort`, `hook_event_name`, `error` and `last_assistant_message` (never `error_details` in the cases seen), and `error` is only a hint. The credit refusal (a 400) arrives as `billing_error` with the CLI's own words `Credit balance is too low`; a 402 and the spend-limit 400 arrive as `unknown` with `API Error: 402 …` / `API Error: 400 You have reached your specified API usage limits. …`; a 401 is `authentication_failed`; a 403, a hold included, is `authentication_failed` too (`Failed to authenticate. API Error: 403 …`); a 429 is `rate_limit`; a 529 is `server_error`; a malformed request (400) and a success fire nothing. The plan's guess ("map `billing_error` and `invalid_request` to classify the text") was therefore too narrow. `signalFromHook` returns no signal for `server_error`, `overloaded`, `max_output_tokens`, `model_not_found`, `oauth_org_not_allowed` and `cloud_credential_error`, and for every other code reads the text: the status only from the CLI's own prefix (`API Error: <3 digits>`, `Failed to authenticate. API Error: <3 digits>`, `API Error: Request rejected (<3 digits>)`), anchored at the start, else from the hint (`authentication_failed` 401, `rate_limit` 429, `account_on_hold` 403). A 402 stands for `billing_error` (the payload has no error type; the plan's table maps a 402 `billing_error` to exhausted). **A tier cap cannot be told from a plain 429 here** (no error code in the text), so it reads as `limited`: nothing happens, the safe direction. The signal keeps the message cut to 256 characters and the resume date read from the whole message; nothing else of the payload (KP12). Fixtures: `apps/connections/test/fixtures/stopfailure/*.json`, the real payloads with ids and paths replaced. Sources read 2026-10-26: https://code.claude.com/docs/en/hooks.md (StopFailure), https://code.claude.com/docs/en/env-vars.md (`CLAUDE_CODE_MAX_RETRIES`, the 429 retries).
32. **What the hook does with a signal, and who it blames** (`KeyPoolService.reportRefusal`). It classifies with the pool's dialect and applies only a credit refusal (exhausted); a refused key (failing) is named to be probed (decision 37). A rate limit, an unknown answer or an ok changes and writes nothing, not even `KeyLimited`: a hook fires on every limited turn and must not fill the event list. An unmatched 4xx raises the one `unclassified` alert (status and error type only, once per change). The command is `keypool report <pool> (--served | --member M | --grant G) --from-hook`, exactly one target: stdin at most 64 KB (`too_big`), invalid JSON `payload`, not a refusal `ignored` (exit 0: the CLI ignores the hook's exit code), one line `{"pool","outcome"}` and never the text. **`--served`** (the form for an interactive session with a hand-written `lease --pool` helper, the case the plan means): the hand-written helper is exec'd by the agent CLI, so the parent of each `lease --pool` call is the CLI, and the hook, a descendant of the same CLI, finds the member by the `KeyServed` events of the pool's members whose caller's parent is its nearest ancestor (up to five levels up, within the hour, the helper's cache being minutes), newest first. Nearest first, so a key leased by hand from a shell further out is not taken for the CLI's. No such event is `unserved` (exit 1, nothing changes). **QA showed why a named member is not enough:** with `--member k1` in a hand-written hook and the rotation serving k2, k2's refusal exhausted k1. `--member` stays for a settings file whose helper is one fixed member. `--grant` is the holder's form for a hook under a pooled run (the grant's session member, decision 14, KP18's window and suspect probe included); by `--member` the member must be in the pool. **A pooled `run`'s own settings carry no hook**: the real CLI in `-p` exits as soon as the turn ends and kills a hook that has not finished (a hook that waits 0.2 s never finished; the launcher's node hook was killed before it wrote), and `run` is always `-p`, where the wrapper already reads the result at the end (decision 1 of slice 1). So the plan's "the launcher's `--settings` carries the hook" is not built; the hook is for interactive sessions.
33. **A sink is a file a pool's key is written to, registered by the principal** (KP20, plan 3.6). `keypool sink add|remove|list <pool> [path]`: absolute, normalised, closed alphabet (`A-Za-z0-9._@+=,:-`, no space, glob, quote or control character, so a path is one literal in a deny rule), at most 16 a pool, one pool per path, never a `.member` path, never in the connections home (`sink_protected`) and never a directory (`sink_directory`). The path is in the saved body and in no event (the events carry a count) and in no `keypool list` (the hub forwards it). **Every sink of every pool and its sidecar are in the deny lists of a `run`** (`permissions.deny` and `sandbox.filesystem.denyRead`), because any lane may read any sink; the lists are built at the run's start, so a sink registered later is denied from the next run on. The lease check for a hand-written launcher (`caller-proof.ts`) is not changed: it cannot name sinks the external launcher does not know. Limit, stated: a hand-written launcher that is not `run` does not deny them.
34. **`write-env` is one gated lease per write** (plan 3.6). `keypool write-env <pool> --file <sink> --var NAME --isolation rules [--if-due [--rotate-every D]]`: the file must be a registered sink; the place is checked before a lease is taken; the pick follows the pool's order; the lease is the probe-style lease of `lease --pool` (reserve 0, holder the writer), `KeyServed` is written, then the file, then the lease closes (`failed` if the write failed). The key goes to `NAME=value` through a temp file in the same directory created 0600 and renamed, then the sidecar `<sink>.member` (the member's name, same way). `NAME` is `[A-Z_][A-Z0-9_]*`, the value `[A-Za-z0-9._~+/=-]`: nothing is quoted or escaped because nothing needs to be. Refused: a path in a git work tree, in a directory group or others can write, through a symlink, or under the connections home. **Deviation from the plan's words** ("a world-readable directory"): a key file is 0600, so what a directory open to others adds is the chance to replace or unlink it; the rule built is *writable* by group or others. A 0755 `/opt/app` stays allowed. The isolation is the writer's claim, as for `lease`. `--if-due` rewrites when the sidecar's member can no longer serve or has left the pool, when the file or the sidecar is missing, when the sidecar is older than the file (a write cut short between the two renames), or after `--rotate-every` (round-robin only). Output: the pool, `written`, the member or `why`; never the key or the path. A crash between the two renames leaves the new key with the old member's name until the next `--if-due`, which notices the older sidecar.
35. **`watch` acts on two phrases only** (plan 3.6). `keypool watch <pool> --log <file> (--member M | --sink <sink>) [--once]` reads a server's log for the classifier's credit-balance and usage-limit phrases and reports the member exhausted. A log holds anyone's words, so a hold, a refused key and a rate limit in a log do nothing (decision 4's rule: the hold words mean something only in a structured answer). The line is never printed or kept: a verdict is a word, the signal told to the pool is a canned phrase, a line is looked at up to 8 KB and the rest of a longer line is dropped as it arrives. A member is reported at most once in ten seconds. With `--sink` the member is read from the sidecar at each match, so a rotated file is followed. Without `--once` it follows the log from its end, from the start of a file that is new, truncated or replaced; `--once` reads what is there and exits. What it prints passes the exact-value filter of the pool's keys. **The flag is `--sink`, not the plan's `--env-file`:** Node reads `--env-file` anywhere in its argument list, script arguments included (`node main.ts … --env-file x` exits 9, "x: not found"), so no flag of this bin may carry that name.
36. **Cursor was not the executor for this slice.** The Cursor account hit its weekly usage limit (resets in five days; no credits were bought), so the lane wrote the code itself, tests first for steps A, C and D and tests with the code for step B (the negative controls are what show B's tests red without the guard). The PR says so.

37. **A key is marked failing, or dry on a log's word, only after a real request about that key** (fix round 1, rev-164 findings 4 and 5). The hook's 401 or 403 is one request's refusal, and a 403 can be per resource (a model, a workspace): `reportRefusal` no longer applies a `failing` outcome, it names the member to be probed, and `keypool report … --from-hook` sends the slice 3 suspect probe (one token, the smallest model, the member's own gate, at most one per member per recheck interval) and prints the probe's word (`healthy`, `failing`, `exhausted`, `skipped`, …). A key the provider refuses to the probe too is `failing` by the probe's own path (KP7: the pool blocks until `revive`); one that answers stays active. A credit refusal (the provider's own words about the key) is still applied directly. `watch` treats the credit and usage-limit phrases the same way: a log line is anyone's words (user text, a lane-written log), so the phrase is a **reason to probe** the member, never a verdict, and a forged line costs at most one probe per member per interval. The cost of that safety: after a probe that found the key healthy, a genuine dry spell is not probed again for the interval; the daily recheck and `keypool report` are the backstops.
38. **`watch --sink` blames the key the server loaded, not the file's later member** (finding 1). The sidecar is now two lines, the member and a stamp of the file it is about (`<inode>:<mtime ms>` as just renamed). `watch` reads the stamp at each phrase: no stamp, a pair that does not agree (the file was replaced or the write was cut short), or a file written less than `--grace` seconds ago (default 600: a server that has not restarted still holds the key before) blames no one and sends nothing; after the grace it is the stamped member. A restart is not observable from here, so a phrase that persists past the grace is what blames the new key.
39. **`write-env` is one writer at a time and the pair always agrees** (findings 2, 3, 9). `<sink>.lock` (the writer's pid, `wx`, stale when that pid is gone or the lock is ten minutes old, waited for up to five seconds, else `busy`) is taken after the checks and held over the due check, the pick and both renames; the pool is read again under it. The key file is renamed first and the sidecar, stamped with that file, second: a reader that sees the pair in between, or after any other writer, sees a stamp that does not agree and acts on nothing (`--if-due` rewrites). The temp files have fixed names, `<sink>.tmp` and `<sink>.member.tmp`, a stale one is replaced and a link in their place refused, so a write killed half way leaves a file the deny list names. Two takers that both find the same stale lock can still both take it (one removes the other's fresh lock): the stamp is what then shows a disagreement; stated, not closed. `--rotate-every` takes seconds, minutes, hours or days.
40. **A sink that holds a key stays denied until its file is gone** (findings 6 and 7). Removing a sink, or deleting its pool, moves the path to `retired` (at most 64 a pool; a deleted pool's go with its tombstone); the deny list of every `run` names the files of the live sinks and, for a retired one, whatever of `<path>`, `<path>.member`, `<path>.tmp` is still on disk. A sink remembers when it was registered (one without a time counts as registered after every run, decision 45); the deny list of a run is fixed at its start, so `write-env` refuses with `older_runs` while a run (a non-probe lease of any key connection) that began before the registration is live. A reserved suffix (`.member`, `.tmp`, `.lock`) is never a sink.
41. **A served key is matched by the parent's identity** (finding 8). `KeyServed` records `parentStartedAt` beside `ppid`; `--served` matches an ancestor by pid and start time, and an event without a start time (older builds) never matches.

42. **Fix round 2 (rev-164b): `watch --sink` blames what the reader can prove the server loaded.** The ten-minute grace of decision 38 is gone: after it a server that never restarted still held the old key while the new member was probed. The sidecar now keeps the last eight writes (`<ms> <member>`, newest last) and `watch --sink` needs the server itself: `--server-pid N`, or `--server-pid-file F` re-read at each phrase so a restart is followed. The server's start time (`/proc/<pid>/stat` field 22 over 100 ticks a second, added to `btime`) names the write that was the file then: the member of the last write at or before it. No server pid, a pid that is no process, a pair that does not agree, or a server older than the first write on record blames no one and sends nothing. The two options are `--sink` only and exclusive.
43. **(Superseded by decision 49.) A lock is created with its owner in it, and is stale only when the owner is provably gone** (decision 39 amended). `<sink>.lock` holds `<pid> <start ticks>`; it is written to a temp file and linked into place, so it never exists empty. A lock that does not read as that (empty, partial, unreadable, the older bare-pid form) is an unknown owner: `busy`, never removed. A parsed owner is gone when no process has that pid or the pid now has other start ticks (reused); then the lock is removed only if it still reads as it did. A live owner is never stale however old the lock: the ten-minute rule is removed, and a lock held by a hung writer needs a person.
44. **A retired sink is never dropped for room** (decision 40 amended). The list is capped at 64 a pool; past the cap `sink remove` is refused with `retired_full` and the sink stays registered. Entries leave only when their files are gone: `sink add` and `sink remove` first forget every retired sink none of whose files (`<path>`, `.member`, `.tmp`) exists (`pruneRetired`). A deleted pool's retired list (in its tombstone) is not capped and is denied only while a file exists.
45. **A sink with no registration time counts as registered after every run began** (decision 40 amended). A pool saved before sinks had times has `sinkSince` empty: `runsPredating` then treats any live non-probe run lease as predating the sink, so `write-env` refuses with `older_runs` until those runs end. The finding says "registered at the epoch"; read literally that would make no run older and the check never fire, so the safe reading is built (the sink is as new as possible). No key pool exists on any machine yet, so the default costs nothing today.

46. **A start time known only to the second blames no one near it** (fix round 3, rev-164c). `/proc/stat` gives the boot time in whole seconds, so a process start computed from it can be up to a second early, and a write just after the real start could look like it came before. `processStartWindow` returns `{ from, to }` (one second wide) and `memberLoadedAt` answers null when a write falls inside the window; otherwise the member of the last write at or before `from`. A server started within about a second of a write is therefore never blamed for it; the real starts are far enough from the writes that this costs nothing in practice.
47. **(Superseded by decision 49.) A stale lock is taken over by one rename of the exact file that was read, and a newer lock is put back** (decision 43 amended). Reading, comparing and then removing (the round 2 form) leaves a gap in which a live lock can be made and removed. Now the taker moves the lock to a unique name in one atomic step, reads what it moved, removes it only if it is the stale text it read, and otherwise links it back where it stood and says `busy`. `release` removes the lock only if it still reads as the owner text this process wrote. I chose this over a kernel lock because Node has no `flock` and `flock(1)` is not on every platform this bin runs on, and over a second "takeover" lock because that only moves the staleness question one level down. **Residual, stated:** between the rename and the link-back there is a window in which a third taker could create a lock; the put-back then finds one standing and leaves it, and the holder it was moved from has lost its lock. That needs a stale lock, two takers and a third arrival inside a few microseconds.
48. **(Superseded by decision 49.) Anything that cannot be proved gone is busy** (decision 43 amended). The lock records the pid namespace of its owner (the inode in `/proc/self/ns/pid`) beside the pid and start ticks. A pid is looked up only in the namespace it belongs to: a lock from another namespace, or one written without a namespace (the round 2 form), or a taker whose own namespace cannot be read, is `busy` and never taken over.

49. **The write lock is a kernel lock, so nothing is ever stale** (fix round 4, rev-164d; **supersedes the lock parts of decisions 39, 43, 47 and 48**). Three rounds of staleness rules for a lock file (a pid and start ticks, a pid namespace, a rename takeover with a put-back) each had a race, and the last three findings were all of one kind: deciding that a lock is dead by looking at files. The lock is now `BEGIN EXCLUSIVE` on an empty SQLite database, `<sink>.lock`, held for the critical section (the due check, the pick and both renames). SQLite's file lock is an fcntl/flock lock: **the kernel releases it when the holder dies**, in whatever pid namespace or container the holder lives (they share the filesystem), so there is no staleness to judge and no takeover. **Why this and not `flock`:** Node has no `flock` and `flock(1)` is absent on macOS, where this bin also runs; `better-sqlite3` is already a dependency (the connections store) and gives the same kernel lock on Linux and macOS. Taking it polls in an async loop with `busy_timeout = 0` (50 ms, up to `waitMs`), so the timers of the process keep running. `<sink>.lock.owner` (pid, start ticks, pid namespace of the holder) is written after the lock is taken and removed on release only if it still reads as written; it is **information for the busy message and never decides anything**. A busy write prints `busy`, then one line that names the holder (`pid N (pid namespace M)`) and the command to look at it (`ps -o pid,lstart,args -p N`, or "another container or pid namespace: look there"), or `fuser <sink>.lock` when no note can be read. There is **no forced takeover of a lock whose holder is alive**, and none is needed for a dead one. Anything at the lock path that is not an SQLite database (or a symlink) is busy and left untouched. **Migration:** none (removed by decision 50: the text locks never shipped). **Limits:** a filesystem without working POSIX locks (some network mounts) gives no mutual exclusion, as for any file lock; a holder killed with SIGKILL can leave an empty `<sink>.lock-journal`, which the next taker's SQLite removes; its owner note stays until the next write replaces it, so for a moment a busy message can name a holder that has died.

50. **Fix round 5 (rev-164e): one handle on the lock file, and no migration** (decision 49 amended). (a) A POSIX file lock belongs to the process, and closing any descriptor of the file releases it. The lock file is therefore opened by one SQLite handle and by nothing else in the process (no read, open or create of it; `lstat`, `access` and `chmod` by path open no descriptor), and an in-process registry, keyed by the real place of the lock file, makes a second taker of the same sink in this process wait for the first (up to `waitMs`) or be busy: it never reopens the file. (b) The migration of decision 49 is removed: the text locks of rounds 2 and 3 never shipped (the PR is unmerged), and deleting a file that matches their shape could delete a live lock; any non-SQLite file at `<sink>.lock` is busy and is never deleted. (c) `release` removes the owner note while it still holds the lock and lets the lock go after, so a taker never sees a note of a holder that has let go (the limit stated in decision 49 now remains only for a holder killed with SIGKILL).

## Not in slices 1 to 4

The organization reader (a probe's response header could feed it; the owner's confirmation stays the whole check), the web card and the phone alert (slice 5), units for `write-env` and `watch` (an example is in the PR; the updater's install list is not changed), the local gateway. The `StopFailure` hook reports for a pooled `run` (its grant) and, by `--member`, for a hand-written settings file; an interactive session puts `keypool report <pool> --served --from-hook` in its own settings (decision 32).

## Alternatives

| Option | Verdict |
|---|---|
| Skip a failing member and carry on | Rejected for v1: it moves traffic to another account because one was refused (decision 4). A later skip for `rejected` only is possible. |
| A local gateway that sees every response | Deferred (ADR-0018 deferred it): exact reporting and per-request rotation, at the price of a proxy in the key path. |
| Pool members as a field of the Connection | Rejected: a Connection must not know its siblings (CN15). |
| Pool inside the account Pool | Rejected: subscriptions have seats, windows and marks; keys have credit. Different rules. |
| Pick and write one event after the gate, saving the last pick once | Rejected: two concurrent picks would take the same member. |

## Consequences

- **Good:** two or more prepaid keys are used one after the other with no hand-switching; a dry key costs one refused request; nothing about a single key changes.
- **Cost:** one table, one aggregate, one service, one classifier, one CLI command group, and a lifecycle hook on `ConnectionsService`.
- **Limit:** a key that runs dry in an interactive session is served until it is reported (the hook of decision 32, `--served`, does that by itself in an interactive session); after a report the loss is bounded by the helper's 60 s cache.
- **Limit:** through the failure hook a tier cap reads as a rate limit (decision 31); the daily probe and the owner's `report` are the backstops.
- **Limit:** `write-env` leaves a key on disk at a path the owner chose, 0600; a process of the same user can read it, as it can read the vault (ADR-0018). The deny list keeps a `run`'s tools off it; it does not cover a launcher that is not `run`.
- **Limit:** the hold words (`account_on_hold`, `authentication_failed`) mean a hold only on a 401, a 403 or a structured result with no status; a 400 that echoes them reads as nothing.
- **Limit:** a record a refusal is read from is the agent CLI's own, but its `result` text for an API error is the CLI's rendering; the classifier matches the credit and spend-limit phrases in it. A different phrasing in a later CLI version reads as nothing (the key is not skipped) until the fixtures follow. A successful run, interactive session or run with another output format is never read.
- **Limit:** keys of one organization share its rate limits and monthly cap; a pool gains nothing against a 429 or the cap.
- **Limit:** the ownership check is the owner's confirmation, not a proof (decision 6).
