# ADR-0008: Patterns borrowed from Signal

- **Status:** Accepted, 2026-10-02. A comparison of Signal's design with Morndo's was accepted, with a requirement to close the gaps. Lane B wrote the brief; lane signal builds it on `feat/signal-patterns`.
- **Constraints:** the product lane's answer on push, linking and the outbox (an internal decision record, §12) is binding. It is folded in below and in `docs/domain.md` (N1–N5, AC10–AC13, S4–S8, O7–O9).
- **Number:** 0002 and 0003 belong to the product lane (ADR-0007, "Number").
- **Builds on:** ADR-0004 (the web endpoint, modeled on Signal), ADR-0005 (stack), ADR-0006 (the desktop client).

## Licence: designs, never code

The Signal source read for this ADR is AGPL-3.0-only: Signal-Desktop at 832279c (2026-10-01), Signal-Server at 2d22cc4, and Signal-Android's `jobmanager` only, all under `~/research/signal-src/` (read-only). Morndo has no licence yet, and copying AGPL code would bind it.

So **we copy designs, never code.** Every piece below is our own implementation, written from a description of the behaviour. Each row cites the Signal file we read as the design reference, with line ranges, so a reviewer can check that only the idea crossed over. No Signal identifier, comment or test was copied, apart from generic names for the same idea (a "missing case" error, a token bucket).

## Context

ADR-0004 took Signal's device model for the web endpoint: linked devices, a pinned identity, a sequenced feed. A read of Signal's code against Morndo's on 2026-10-02 found the gaps a messaging client closes after years in production, and Morndo had not:

1. **Robustness:** the hub's schema grows by ad-hoc `ALTER TABLE`; inbound frames are trusted by shape (`as Incoming` in the web app; an empty `requestId` is accepted at `http.ts:209`); a throw in the terminal socket's `message` handler is an unhandled rejection, which ends a Node 24 process; one global bucket rate-limits pairing and login for every caller; nothing prunes old tokens and sessions; the hub logs with bare `console.*`.
2. **Liveness:** only the feed socket is pinged, and only by the hub. The app reconnects on `visibilitychange` only when its socket is already gone, so a phone that slept can sit on a dead socket showing "Live".
3. **Sending:** a send lives in a Svelte variable. A reload, a crash or a closed tab loses it; the hub's dedupe of request ids is in memory, so a restart mid-type can type it twice; a blind 20-second timer drops the "sending" entry whether or not it arrived.
4. **Reading:** no drafts, no read state across devices, no "new messages" divider, no jump to the latest, and nothing older than the latest 300 messages.
5. **Devices:** only the console can issue a pairing token, so adding a laptop needs the box.
6. **Notifications:** none. The principal learns that a decision waits only when he opens the app.
7. **Tooling:** no lint, no CI, no place to see every UI state at once, no size budget.

## Decision

Each row: what Signal does (the design reference), what we take, and what we change and why. Phases A to G are the build order on the branch; each ends green with an independent review.

Paths are under `~/research/signal-src/`; `D/` is `Signal-Desktop/`, `S/` is `Signal-Server/service/src/main/` (`java/org/whispersystems/textsecuregcm/` for Java files). "L" gives the lines read.

### Phase A: foundation

**A1. Numbered migrations.**
- *Signal:* one ordered list of `{version, update}`; the version lives in SQLite's `user_version`; every pending migration runs in one transaction and `user_version` is set at its end, so a throw rolls the whole batch back; a database newer than the newest migration is refused with a "start the newer version" error that offers no "delete data" (`D/ts/sql/migrations/index.node.ts` L1717-1805, L1751-1756, L1785; `D/app/main.main.ts` L1958-1969). The list is asserted monotonic at boot (L1730-1740).
- *We take:* all of it: `user_version`, an ordered list, one transaction (`BEGIN IMMEDIATE`) for every pending step, refusal of a future database, a monotonic check.
- *We change:* versions count 1, 2, 3 without gaps (Signal steps by 10); no `VACUUM` split, since we have no migration that needs one. Migration 1 is today's schema and migration 2 is today's ad-hoc `sessions.verified_at`, each written so that it detects itself as already applied on an existing database (`CREATE TABLE IF NOT EXISTS`, a column check). A future database makes the hub print one sentence and exit 78 (EX_CONFIG): there is no window to show a dialog in, and a dedicated code lets the service manager stop restarting into the same refusal (`RestartPreventExitStatus=78` would do it; the unit is the owner's). The version is read again under the IMMEDIATE write lock, so two processes opening an old database don't both migrate it.

**A2. A shared wire protocol package, `packages/protocol`.**
- *Signal:* parses untrusted input with zod 4 schemas through one pair of helpers, `parseUnknown` and `safeParseUnknown` (`D/ts/util/schemas.std.ts` L111-120; `D/package.json`: `zod` 4.3.6); the wire itself is protobuf.
- *We take:* one schema per WebSocket message type, both directions, and per HTTP JSON body; every inbound frame and body is parsed before use, on the hub and in the web app.
- *We change:* no protobuf: our frames are JSON over one hub. A malformed frame closes the socket with 1003 on the hub (as today) and is dropped in the web app, which never crashes on it; an unknown type is ignored, so an older client survives a newer hub. The two directions differ on purpose: what the app sends the hub is strict and size-limited; what the hub sends the app is checked for shape, not size, an enum value the app doesn't know falls back to a safe reading, and a list (workers, messages, attachments, decisions) loses only the element that doesn't fit, never the whole frame (review M1: one long tmux window name used to leave the app on "Connecting"). A contract test runs the hub's own output through the app's schemas. `requestId` must be a UUID. `packages/domain` stays dependency-free: the schemas live in their own package, which the domain never imports. zod or `zod/mini` is decided with a measured bundle size (below).

**A3. `unreachable(x: never)`.**
- *Signal:* `missingCaseError(x: never)` returns a TypeError naming the value; it sits in the `default` of every exhaustive switch, so a new union member is a compile error and bad runtime data throws with the value (`D/ts/util/missingCaseError.std.ts` L25-26; used in over 170 files).
- *We take:* the same idea in the domain's `shared.ts`, named `unreachable`, used in every switch over a union, starting with `feed.svelte.ts`, which has no default today.
- *We change:* nothing of substance; it throws rather than returns, so a call site needs no `throw`.

**A4. A hub logger that redacts every line.**
- *Signal:* every log line passes one composed redactor: ids keep their last 3 characters so lines stay linkable; phone numbers, group ids, card numbers and registered sensitive paths (the home directory first) are replaced (`D/ts/util/privacy.node.ts` L16-34, L124-236; `D/app/privacy.main.ts` L9-13). `toLogFormat` logs an error's stack, or only "HTTPError <code>" for HTTP errors so no body leaks, plus one "Caused by" line (`D/ts/types/errors.std.ts` L6-26). Lint forbids `console` ("use our logger", `D/.oxlintrc.json` L922).
- *We take:* levels and one sink that redacts every line; `toLogFormat(err)` with name, message and stack, never bodies; no `console.*` in the hub.
- *We change:* what is redacted is ours: emails, `*.ts.net` host names and tailnet addresses (100.64.0.0/10), cookie values (`__Host-morndo=`), bearer tokens, pairing secrets (`t=`, `#t=`), and the home directory written as `~`. The cause chain is walked to the end, with a depth cap (Signal follows one level and drops the cause's stack).

**A5. Crash safety.**
- *Signal:* the main process registers `uncaughtException` and `unhandledRejection` handlers that report through its error path (`D/app/global_errors.main.ts` L80-87).
- *We take:* process-level handlers that log through the logger, then exit 1. The service unit restarts the hub (`Restart=on-failure`, `RestartSec=5`; read, not changed).
- *We change:* we also fix the cause we know: the terminal socket's `message` handler is async with no `try`/`catch` (`http.ts` L407-415), so a throw in it is an unhandled rejection, which ends a Node 24 process. The crash harness (`http-crash-fixture.ts`) proves the fix.

**A6. A token-bucket rate limiter with `Retry-After`.**
- *Signal:* a token bucket per limiter and key, refilled continuously, run atomically in Redis; configs are `{bucketSize, permitRegenerationDuration}`; a refusal is a 429 whose `Retry-After` is the deficit divided by the refill rate (`S/.../limits/RateLimiter.java`, `LeakyBucketRateLimiter.java` L71-117, `RateLimiterConfig.java` L12-27, `RateLimiters.java` L19-87; `S/resources/lua/validate_rate_limit.lua` L1-62; `mappers/RateLimitExceededExceptionMapper.java` L27-38). Per-IP limits key by the remote address (`RateLimitByIpFilter.java` L56-93).
- *We take:* `{capacity, refillPerSecond}` per key, 429 with `Retry-After`, keys per caller.
- *We change:* in memory, because there is one hub process. `Retry-After` rounds up to whole seconds (Signal's mapper truncates, so 1.2 s becomes "1" and the client comes back too early). Pairing and login are keyed per caller (the `Tailscale-User-Login` header, else the remote address) with a looser global ceiling, so nobody can lock the owner out by spending one global bucket. Sends and answers are limited per Endpoint; uploads stay at 60 a minute per Endpoint, as a bucket; feed frames per connection, closing with 1008 on abuse. The web app honours `Retry-After`.

**A7. Lint.**
- *Signal:* oxlint with type-aware rules switched on in the config (`"typeAware": true`, backed by `oxlint-tsgolint`), `no-floating-promises`, `no-misused-promises` (with `checksVoidReturn: false`) and `await-thenable` as errors; fire-and-forget is spelled out with a one-line `drop(promise)`; `switch-exhaustiveness-check` is off and `missingCaseError` covers exhaustiveness (`D/.oxlintrc.json` L3-6, L455, L467, L737, L775; `D/ts/util/drop.std.ts` L6-8).
- *We take:* oxlint, type-aware through the config, if its type-aware `no-floating-promises` is documented as stable (else typescript-eslint, per the brief); `npm run lint`; an explicit `void` is the allowed way to fire and forget.
- *We change:* `switch-exhaustiveness-check` on as well: our unions are few and small, and the rule catches a switch that forgets `unreachable`.

**A8. Retention.**
- *Signal:* prunes what it no longer needs on a schedule, for example persisted sync tasks after 5 attempts and 2 days (`D/ts/util/syncTasks.types.std.ts` L4; `D/ts/sql/Server.node.ts` L2552-2557).
- *We take:* pruning on start and daily.
- *We change:* our own limits: pairing tokens expired or redeemed more than 30 days ago, sessions ended more than 90 days ago; from phase C, send records after 24 hours (S5), and from phase E, finished Link requests. `audit` and `decisions` are never pruned: they are provenance (A1, E8).

### Phase B: connection liveness

- *Signal:* an application-level keepalive every 30 s after the last success, with a 30 s timeout, one probe in flight; if the last success is over 5 minutes old (the machine slept), the socket is closed at once instead of probed; on resume a keepalive is forced; `offline` switches to a longer backoff and probes with a 5 s timeout; `online` cancels the pending wait and connects now. Reconnects back off along 1, 2, 3, 5, 8, 13, 21, 34, 55 s (then up to about 26 min while offline), with up to 5 s of jitter on steps of 8 s and more (`D/ts/textsecure/WebsocketResources.preload.ts` L499-649; `D/ts/textsecure/SocketManager.preload.ts` L57-100, L256-297, L535-589, L749-762; `D/ts/util/BackOff.std.ts` L8-29, L58-84).
- *We take:* an app-level ping (`{t:"ping",n}` / `{t:"pong",n}`), `lastAliveAt` refreshed by any frame, reconnect at once after 5 minutes of silence, a short probe after a wake, Fibonacci backoff with jitter, `online` resets and reconnects at once.
- *We change:* faster numbers, because the principal's phone is the client and a dead "Live" is the failure: a ping every 25 s, no pong in 10 s means close and reconnect; on `visibilitychange`→visible, `pageshow`, `focus` and `online`, no socket connects now, silence over 5 min reconnects now, over 30 s probes with a 5 s timeout. Backoff 0.5, 1, 2, 3, 5, 8, 13, 21, 34 s plus up to 1 s of jitter. While offline we stop retrying and show "Offline" (Signal keeps retrying slowly); because MDN calls `navigator.onLine` unreliable, Offline is never sticky: a wake, or a look every 30 s, reconnects once the browser says online again. A wake while a handshake is under way changes nothing, and a handshake that hasn't finished in 10 s is given up. A browser reports a refused upgrade (signed out, revoked) as close code 1006, like any network failure, so after a handshake that failed the app asks `/api/me` and a 401 ends retrying ("Signed out"). The backoff resets on the hub's first frame, not on open. The hub also pings the terminal and desktop sockets and counts any message from them as alive (a pong can queue behind desktop frames); the terminal view uses the same backoff and the same session check. Known limit: a hub older than the app ignores `ping`, so the app would reconnect every 35 s until both are the same version (they ship together).

### Phase C: durable outbox and send states

- *Signal:* a job is written to the database before it runs; jobs come back in order after a restart and a new job never overtakes a restored one; one serial queue per conversation, parallel across conversations; a wall-clock retry budget of 1 day from the job's creation, which survives restarts; backoff ×1.9 per attempt, capped at 15 min; before each attempt, wait for `online` within the budget; on giving up, the job marks the message failed (`D/ts/jobs/JobQueue.std.ts` L181-196, L327-342; `D/ts/jobs/JobQueueDatabaseStore.preload.ts` L32-72; `D/ts/jobs/conversationJobQueue.preload.ts` L339-340, L506-510, L851-898; `D/ts/jobs/helpers/commonShouldJobContinue.preload.ts` L14-64; `D/ts/util/exponentialBackoff.std.ts` L7-55). A send status is ranked and the reducer keeps the higher rank, so late receipts never move it back; a manual retry is the one way back from Failed (`D/ts/messages/MessageSendState.std.ts` L52-60, L105-159).
- *We take:* an outbox in IndexedDB written before the first POST, one serial queue per conversation, a wall-clock budget from `createdAt` that survives a reload, waiting while offline, forward-only send states, and a manual Retry that keeps the request id.
- *We change:* the budget is **2 minutes**, not a day: an agent acts on what it is told, and an instruction that arrives late can be wrong (decision below). Backoff 1.5, 3, 6, 12 s, then 15 s, honouring `Retry-After`. The hub's dedupe becomes durable in SQLite (S5): `started` before typing, `done` after; a replay of `done` is `duplicate`, a replay of `started` is `uncertain` (409), never a retype, and the app says "May have been sent: check the conversation". Each Command carries the needs-you state it saw and is refused as `stale` if that changed in either direction (S6, the product lane's constraint): "The question changed: review before sending". The terminal adapter's own refusal to type into a menu (`menuOnScreen`) stays as the last guard; the `stale` check runs first so the reason is clear. A step-up that went stale while queued gives "Not sent: verify", one tap. Retry is offered only while the hub still holds the request's record (24 hours, S5); an Uncertain send offers Discard only. The upload registry is persisted, so a restart no longer gives `unknown_upload`. Our last state, Echoed (S8), is the principal's own message showing up in the transcript: an echo removes at most one pending entry, the oldest, and only from messages newer than `createdAt` minus 5 s; today's blind 20-second cleanup goes. An entry still unseen after 10 min says "Sent, not seen in the conversation yet".

From the phase C review, each a rule now: a message carries what the worker waited for when it was *started* (the box going from empty to something), not at Enter; a refusal after the paste (`not_submitted`), or a throw while typing, keeps the request's row so a repeat is `uncertain`, never typed twice; one POST is given up after 15 s (or the time left) and Discard is offered while it is Queued or Sending; a message Not sent or Uncertain holds the later ones of its conversation until Retry or Discard (Signal keeps order the same way, per conversation); the hub returns its own time of the typing so echoes are matched on the transcript's clock; tabs share one sender through a Web Lock and tell each other of changes; Retry is offered only while a full 2 minutes would end inside the hub's 24-hour record. Known limits: an echo is matched on exact text, and Edit brings back the text but not the images.

### Phase D: reading comfort

- *Signal:* drafts save with a 100 ms debounce and a per-composer send counter drops a stale debounce, so a sent text never comes back (`D/ts/state/ducks/composer.preload.ts` L1166-1173, L1552-1603, L1806-1809). Read state is a watermark ("read up to here"), synced to the other devices and only moving forward, clamped to now (`D/ts/util/markConversationRead.preload.ts` L36-100, L226-266; `D/ts/messageModifiers/ReadSyncs.preload.ts` L165-257). The timeline picks its scroll anchor with one pure, exhaustive function: nothing, bottom, an index, the unread divider, keep the top offset, keep the bottom offset (`D/ts/util/timelineUtil.std.ts` L31-38, L157-209). It shows a last-seen divider with the unseen count, and a scroll-down button with the count of unread messages below; older messages load when the first row becomes visible and keep the bottom offset (`D/ts/components/conversation/Timeline.dom.tsx` L53-59, L280-355, L459-491, L736-866, L1144-1160, L1205-1215).
- *We take:* drafts with a send-counter guard; a forward-only read mark synced through the hub; the "new messages" divider; a jump-to-latest button with a count; older pages that keep what is on screen in place; the scroll anchor as a pure, exhaustive function with unit tests.
- *We change:* drafts are text only, per device, in `localStorage` (`morndo.drafts`), debounced 300 ms. Read marks are a row per Conversation on the hub (`read_marks`), clamped to the hub's clock (Signal clamps to now too), sent as `{t:"read", conversation, at}` (the worker's name) only while the conversation is open, the page visible and the list at the bottom; the hub broadcasts it and the snapshot carries every mark; the old `morndo.read` is uploaded once (the hub keeps the maximum). Mute moves to the hub the same way, because push needs it there. The divider is captured when the conversation opens and stays until you leave. Older pages are read backwards from the transcript in byte chunks, 100 messages at a time, for the asking Endpoint only (O9); the client keeps up to 1500 and trims the far end.

From the phase D review, each a rule now: a draft is keyed by the worker's pane and kept with its name, and comes back only where both match (two panes can share a name), with what the worker waited for when it was started, so a restored draft is still refused as `stale` if the question changed; each save rewrites only its own entry, so tabs keep each other's drafts. Each transcript line is parsed once per older page, the hub remembers where each page began so the next reads only what lies before it, and the scan stops after 64 MB; an older page the hub can't read is `missing` ("Couldn't load older messages", Try again), never the beginning. An older page keeps the first message on screen exactly where it was, even when the cap trims the newest end in the same change, and the line above the messages ("Loading older…") has a fixed height so it never pushes them down. A read mark covers only the last message the list holds, never while the newest are trimmed away, and the list says it is no longer at the bottom when it goes (another conversation, view or tab). A reconnect keeps the older pages read. Sending while reading far back brings the latest back. The hub keeps at most 500 read marks. Known limit: read marks, mute and the device's own conversation settings are keyed by the worker's name, as before this branch, so two workers with the same name share them (drafts no longer do).

### Phase E: adding a device from an active device

- *Signal:* the new device opens an anonymous provisioning socket, gets a one-time address and shows it with a fresh public key as a QR code, rotated every 45 s; the primary scans it, asks the server for a link token (account id and time, HMAC-signed, 10 minutes, single use, written used in the same transaction as the new device; at most 6 devices, checked on issue and on link) and sends it to that address encrypted; the primary long-polls for the linked device. Linking is rate-limited per account (`D/ts/textsecure/Provisioner.preload.ts` L96-107, L260-352, L420-436; `S/.../controllers/ProvisioningController.java` L36-104; `S/.../controllers/DeviceController.java` L91-115, L166-323, L325-385; `S/.../storage/AccountsManager.java` L205-208, L715-869; `S/.../limits/RateLimiters.java` L28-29, L57).
- *We take:* both directions. "Add a device" on an active device issues a pairing token (10 min, single use, AC1) shown as a QR code and a link. "Link with a signed-in device" on the new device creates a Link request, shows its QR code, and an active device approves it; the new device then continues the normal pair flow (fingerprint check, then passkey). The 6-device cap holds (AC2).
- *We change:* no extra encryption layer for the token: the hub is the only server, reached over the private network and TLS (ADR-0004, "Signal Protocol" rejected). The new device polls `GET /api/link/<id>` with its secret instead of holding a socket. From the product lane (AC10-AC13): a fresh step-up on the issuing or approving device; a 6-digit code on both screens in both directions, which Signal doesn't have; the approval shows when the request came and the network identity header; every active Endpoint is told; the new Endpoint starts with no step-up credit. Link requests are unauthenticated, so they are rate-limited per caller, at most 3 open, and live 10 minutes.

Built that way, each a rule now:
- **The requester's token is derived from its own secret.** On approval the hub issues the pairing token with the hash of HMAC-SHA256(key: the requester's secret, "morndo-link-token"), computed when the request was made. It keeps only the hashes of both, so nothing it stores redeems the token, and a restart between approval and collection loses nothing. The token is issued from the approving Endpoint, with the request's code.
- **The secret only in a header.** The new device asks `GET /api/link/<id>` with `X-Morndo-Link-Secret`, never in the address (logs and history keep addresses). A wrong secret and an unknown request get the same 404. Collecting gives the same answer until the request ends, so a lost reply can be asked for again; once approved, the token's own life counts, so an approval in the request's last seconds isn't lost. The token itself is redeemed once (AC1). Cancel on the new device ends the request with the same secret and frees its place among the 3; Cancel on "Add a device" withdraws its token.
- **The pinned identity travels, proven (review M1).** "Add a device" puts its own pin into the link (`/pair#t=…&f=…`), which the hub never sees. In the other direction the hub relays the identity, so the new device's QR code carries a random key in its fragment (`/link#r=…&k=…`) that the hub never sees: the approving device sends its pinned identity with HMAC-SHA256 of it under that key, and the new device trusts the identity only if the HMAC matches. A device without a pinned identity can neither approve nor issue. **Limit, as for every pairing:** the page code that does these checks comes from whatever answers at the origin; a hostile server there can skip them. The checks catch a different hub at the same address (reinstalled, swapped), and protect a device whose app is already cached; against a hostile server at the origin, the defence is the private network and TLS (ADR-0004).
- **Approving needs a passkey check from the last 5 minutes; denying doesn't.** The 6-device cap is checked on issue, on approval and on pairing, as Signal checks on issue and on link, and is said before any passkey prompt.
- **The code is typed, not compared** (the product lane's amendment 11, accepting review L5). In the link direction the approving device types the code the new device shows; it never shows the code itself. In the Add-a-device direction the new device types the code the issuing device shows, before its passkey: the link alone isn't enough, and the pairing page is never told the code. A wrong code ends that request or token at once, with no second try on it; the user starts over. Next to the input: "Type the code from the device you're holding. If someone sent you a code or a QR, stop." A token bound to an approved Link request has no code of its own: its code was typed by the approver. No code at all is asked for, not counted as wrong: the request stays open (review L7). An ended token expires as of its own issue time, so a clock stepping back can't revive it (review L1). Basis: MFA number matching against approval fatigue (Microsoft Entra enables it by default for all Authenticator users, https://learn.microsoft.com/en-us/entra/identity/authentication/concept-authentication-default-enablement, read 2026-10-02; CISA's fact sheet https://www.cisa.gov/sites/default/files/publications/fact-sheet-implement-number-matching-in-mfa-applications-508c.pdf, as the product lane cites it: not verified here, it answers 403 to non-browser requests). **Limit:** typing doesn't stop a live relay, since a lure can carry the code along with the link; the warning line covers that, and AC13's notice to every device catches it afterwards.
- **Expiry** is written when the hub next looks (a `LinkExpired` audit row, once); retention drops requests a day past their life.
- **Limits:** asking 5 at once per caller, then one a minute (under the shared passkey ceiling); polling 60 at once, then one a second.
- **AC13 in the app:** every live feed gets `{t:"linked", name, at, by}` and shows a notice with Review devices. A device that wasn't open hears of it at its next hello (additions since its own pairing, up to 7 days back) until Dismiss or Review there says it has seen them (review M2). The Notification half comes with phase F.
- **A check the app makes on its own** (Add a device asking whether its token was used) carries `X-Morndo-Background: 1` and doesn't count as use, so a page left open doesn't keep a session from going idle (AC5; review M3). It asks about its own token only, and stops when the code runs out.
- **The audit keeps the trail** after a request is pruned: who asked (the network's identity header) and which token an approval bound.
- **QR codes:** drawn by uqr 0.1.3 (MIT, no dependencies, published 2026-04-03, no OSV advisories, 2026-10-02) as SVG with the 4-module quiet zone, loaded only when a code is shown (a 10 kB chunk outside the first load). The hub's `qrcode` 1.5.4 (2024-08-05) brings `yargs`, `pngjs` and `dijkstrajs` and was not taken for the browser.

### Phase F: web push

- *Signal:* notifications coalesce: the latest replaces a single queued slot, shown after a 1 s trailing debounce, and the previous one is closed first, because creating and destroying them too fast left stuck ones; if the window is active when the debounce fires, nothing is shown; the content can be set down to "count only"; in a muted group, a mention or a reply to you still notifies by default, while a muted 1:1 chat never does (`D/ts/services/notifications.preload.ts` L124-133, L179-231, L333-370, L460-463; `D/ts/messages/maybeNotify.preload.ts` L288-313; `D/ts/util/notifyWhileMuted.std.ts` L17-21).
- *We take:* per device the latest wins after a 1 s debounce; a fixed `tag` per kind so a new notification replaces the old; counts only; nothing while the principal is looking; Decisions break mute, as mentions do.
- *We change:* counts only is the only level, not a setting (N1): push services sit outside the machine. "Looking" spans devices and means attending (focus plus input in the last 2 minutes, N3), not merely visible. Triggers are a Decision starting to wait, a worker starting to need you, and a device linked (N2); ordinary agent messages never push. A push is a Notification, never a Delivery (N5). VAPID keys are generated once into `MORNDO_HOME` with mode 0600.

Built that way, each a rule now:
- **Our own RFC 8291 and RFC 8292 on `node:crypto`**, not `web-push` (MPL-2.0, last published 2024-01-16, five dependencies; approved by lane-b with conditions). Encryption reproduces RFC 8291 Appendix A byte for byte; the RFC 8292 example JWT verifies with our verifier; our JWT is ES256 with `aud` the push service's origin, `exp` 12 hours ahead (at most 24), reused per push service until an hour is left (Apple: don't refresh more than once an hour). `sub` is `https://morndo.com` unless `MORNDO_PUSH_CONTACT` sets a contact of the operator's own: the JWT travels in clear to the vendors' push services, and the hub's origin would name the private host (review L2). It was `mailto:push@morndo.invalid` until 2026-10-03, which Apple refuses (see "After the owner's phone test" below). A plaintext over 3993 octets is refused, the most one 4096-octet record holds (RFC 8291 section 4; review L6). The key file is made once even when two processes start together, and made private again if it was readable by others (review L8).
- **Only the browser vendors' push services** are accepted at subscribe (Chrome's FCM, Mozilla's, Apple's `*.push.apple.com`, Microsoft's `*.notify.windows.com`; https, no port), so a session can't make the hub post where it likes. A test's own push service is allowed through `MORNDO_PUSH_EXTRA_ORIGINS`, never set in production.
- **The payload is numbers only** (the product lane's amendment 4): `{kind, decisions, workers, linked}`, the kind as 0, 1 or 2, pinned by a strict schema in `packages/protocol` (`PushPayload`). The service worker builds the words; anything unreadable still shows "Something needs you." (Safari revokes a page that doesn't show one). Accepted (review L2): the push service still sees the kind, through the `Topic`, `Urgency` and `TTL` headers, never the counts.
- **Per kind the latest wins after a second**, counted again when it goes (answered meanwhile: nothing); the RFC 8030 `Topic` is the kind, so a push service also keeps only the newest; TTL 12 h for Decisions, 1 h otherwise; `Urgency` high, normal for workers.
- **Attending**: each feed reports `{t:"visible", v}` on change and a minute after its last report while true, however much input comes in between (review H2); the hub forgets a report after 2 minutes or when the connection closes. While any device attends, due Notifications are dropped, not delayed, except that a device was linked (review M2: the approving device is usually the attending one, so the push meant for the others would be lost, phishing relay included).
- **One push per ask** (review M1): a worker's question or menu is an Ask on the board, so it pushes once, as a Decision waiting, muted or not; the worker kind is left for a need that isn't an Ask (none today). Mute therefore silences a worker's chatter but not its asks, which is what "except for Decisions" says.
- **A key that isn't a point on P-256** is refused at subscribe, and the sender never throws: an unusable key drops its subscription as invalid, and a failing round is logged, never left to end the hub (review H1).
- **On phones** (the narrow layout) there is no Decisions view yet; a notification's tap opens the agents list, which lists who needs him first. Deciding from a phone is the product lane's next question, not this branch's.
- **What already waits when the hub starts raises nothing**: one look at the workers and the decisions first, then only changes count. A first look that fails is tried again up to 5 times, 2 s apart, since an empty baseline would make everything waiting look new (review L4).
- **The subscription** is one per Endpoint (migration 7); revoking the Endpoint or signing out on it deletes it in the same transaction (review L3); a push service's 404 or 410 deletes it, and so does a key that can't be used. The audit keeps PushSubscribed, PushUnsubscribed (device, revoked, signed_out, gone, invalid), NotificationSent (kind, counts, how many devices) and NotificationFailed (kind, status): never who or what. **Known limit** (review L5): any other refusal (403 for a VAPID key the service no longer accepts, 400, 413) is logged and audited but keeps the subscription, so a device whose subscription keeps failing stays listed as on until it is turned off and on again.
- **The toggle** asks the browser only on the tap, then subscribes from the same tap (Safari needs both inside the gesture). On iPhone and iPad outside the Home Screen it explains Add to Home Screen, since iOS gives web push only to Home Screen web apps from iOS 16.4 (Apple, "Sending web push notifications in web apps and browsers", developer.apple.com, read 2026-10-02).
- **Tests:** a fake sender in the hub's tests; the service worker's handlers with fakes; the e2e delivers a push through CDP `ServiceWorker.deliverPushMessage` (it skips encryption) on the full Chromium in new headless mode, because Playwright's default headless shell has no notification permission; and a local push service receives the hub's encrypted push, decrypted in the test as a browser would. A notification's click can't be driven through CDP: its handler is tested with fakes and the deep link it opens in Chromium.

### From the whole-branch review and hands-on QA

Each a rule now:
- **Revoking a device ends the pairing tokens it issued and nobody used** (M1): its Add a device links and the tokens of Link requests it approved, audited as PairingTokenWithdrawn. Now that devices add devices, revoking is how a lost or phished one is contained.
- **Revoking another device needs a passkey check as fresh as a command does** (L8); a device can always revoke itself, and the console stays the way back. A device added from another device has had no check of its own (AC12), so a phished one can't cut the owner's devices off.
- **A Command goes only to the worker it was written to** (M2): the app sends the worker's name, and the hub refuses as `no_pane` when the pane now runs another worker, since tmux gives pane ids out again after a restart and a Retry lives up to a day. An older app sends no name and isn't checked.
- **Signing out, or revoking this device, forgets what was written on it** (L3): the drafts and the outbox's unsent messages. Layout choices and the pinned hub identity stay. An expired session forgets nothing: drafts survive an idle timeout.
- **A feed frame that fails closes its socket** (L5) with 1011 instead of ending the hub; the app reconnects.
- **At most the 50 latest old read marks and 30 mutes go up once** from a device that kept its own (L6), inside the hub's frame limit.
- **The phone's agents list puts who needs you first**, marked "needs you" (hands-on QA: it sorted by name, contrary to the push rule above).
- **Terminal keys reach the pane in the order typed** (found by CI on 2 CPUs; see Phase G).
- **Stopping the hub closes every connection at once** (hands-on QA: a stop took 66 s, because `server.close()` waits for a browser's silent preconnect until Node's 60 s header timeout).

- **Attending drops a Notification instead of delaying it** (L4). A Decision raised within 2 minutes of his last input on a device is not pushed later. Delaying until he stops attending also meets N3; that is the product lane's call.

### After the owner's phone test (2026-10-03)

Two failures on his iPhone, fixed by the product lane (a private QA record, not in this tree), and what an independent review of that fix found. Each a rule now.

**The push contact is one a push service accepts.**
- Apple answered every push with 403 `{"reason":"BadJwtToken"}`. Its documentation lists a subject that "isn't a URL or `mailto:`" under that code [A1]; in practice a contact on a special-use name is refused too.
- Measured against Apple's service on 2026-10-03, with the hub's own key and request and the `TTL` header left out, so an accepted token answers 400 `BadTtl` and nothing is delivered:

  | Contact | Answer |
  |---|---|
  | `mailto:push@morndo.invalid` (the old default), `mailto:push@example.test`, `https://morndo.invalid`, `https://localhost` | 403 `BadJwtToken` |
  | `mailto:push@morndo.com`, `https://morndo.com`, `mailto:push@example.com` | 400 `BadTtl`: the token passed |

- The default is now `https://morndo.com`.
- `isPushContact` takes a contact only as `https://host…` or `mailto:name@host`, written exactly so: printable ASCII, no spaces, no backslash, no login, no query on a mail address. The host is a name of two or more labels (letters, digits and hyphens, none empty), not an address, and not a special-use name: `.invalid`, `.test`, `.example`, `.localhost`, `.local`, `.onion`, `.internal`, `.alt` and `.home.arpa`. Only `.invalid`, `.test` and `localhost` were measured; the rest are refused by the same rule.
- `serve` refuses to start with any other contact: one sentence and exit 78, as for a database from a newer hub. Reading the settings never fails for it, so the console commands (`devices`, `revoke`, `audit`) still work to put things right (review L6). The live unit has no `RestartPreventExitStatus=78` yet, so systemd would still try again every 5 seconds; adding that line is a change to the unit, outside this repository.

**A refusal keeps the push service's reason code, and only a code.**
- The sender reads a refusal's JSON body, at most 4096 bytes and within its timeout, and keeps its `reason`.
- `reasonCode` in the domain says what a code is: letters and digits, at most 64. The sender and the service both apply it, so no sender can put text into the audit or the log (N1; review L8).
- NotificationFailed carries the code, and the hub logs one line per refusal: the kind, the status and the code.

**A prompt absorbed in the middle of a turn is a message.**
- A prompt that arrives while the agent works is taken into the running turn. Claude Code 2.1.284 to 2.1.288 write `queue-operation` records (`enqueue`, then `remove` with reason `absorbed_mid_turn`) and an `attachment` of type `queued_command` holding the prompt, its origin and the time it was sent. They never write a user line.
- The adapter read user lines only. So the principal's own message never came back as an echo and its Sent entry never ended (S8). Lane events, the manager's messages and peers' messages absorbed the same way were missing as well.
- The adapter now reads a `queued_command` attachment through the same rules as a prompt line: the same authors, prefixes and meta rule.
- **Only known sources speak** (review M3): a person at the terminal (`human`) or on a channel, a peer, a background task, in the command modes `prompt` and `task-notification`. Any other origin or mode is no message. A principal's `[tap …]` line answers an Ask, so nothing unknown may come out as the principal. Claude Code 2.1.283 and older wrote an absorbed task notification without an origin; there its command mode says what it is.
- **It is placed where the agent took it in** (review M2). Its own timestamp is when it was sent, but the line is written later, after lines with later times. The adapter gives it the latest time read before it, if that is later; only turns, replies and queue records count for that, not the agent's other bookkeeping lines. The order by time is then the file's order, so the live conversation, a reload and an older page agree, and no page loses it.
  - Accepted: a read that begins exactly at such a line has nothing before it to go by and keeps the sent time.
  - Accepted: the echo's time bound (S8) now sees when the agent took a prompt in, not when it was sent. The same text typed at the terminal just before it was sent from the app, and taken in after, ends the app's entry. That matters only if the app's own send was lost.

**A long paste's wrapper is taken off** (review H1).
- Claude Code writes a long pasted prompt as `<pasted_content id="x">`, the text, `</pasted_content id="x">`. The hub types by bracketed paste, so a long message from the app arrives like this, absorbed or not.
- Under the wrapper the prefix rules missed: the manager's long messages and lane events showed as "You", and the principal's own long message never matched its Sent entry.
- One wrapper with matching ids around the whole prompt is now taken off before anything is read from the text. A wrapper around part of it, or with two ids, is left as written.

**Counts, read-only, 2026-10-03.** Over the 40 most recently changed transcripts in all account directories on this machine: 3330 `queued_command` attachments (2246 typed, 912 task notifications, 172 from peers), and 412 wholly wrapped prompts (354 on user lines, 58 on attachments). The reviewer's own choice of 40 files gave 747 attachments. In neither count was an absorbed prompt also written as a user line.

## Decisions taken by lane-b (reversible)

- **Outbox auto-retry budget: 2 minutes,** then manual Retry or Discard. Signal's is 24 hours, but an agent acts on a stale instruction.
- **A hub restart mid-type gives "uncertain",** never an automatic retype.
- **Drafts are text only, and per device.**
- **Read marks and mute live on the hub,** synced across devices.
- **Push payloads hold counts only.** Push goes only for Decisions waiting, workers needing you and devices linked; mute suppresses everything but Decisions. Nothing is pushed while the principal is attending (N3).
- **Audit and decisions are never pruned.**
- **Both device-adding directions are built,** and each needs a fresh step-up.

## The product lane's constraints (binding, §12)

1. **Notification is a new term, not a Delivery** (N1–N5). Its events are NotificationSent and NotificationFailed, counts only. A push never records DeliveryAttempted or DeliveryFailed: one counts-only ping would satisfy E4 for every Escalation it counts, and EscalationOverdue would never fire.
2. **A Notification and a Read mark grant and start nothing** (N5, O8): no Mandate, Decision, Acknowledgement or Settled state, no timer started, shortened or ended. Basis: A1, O4.
3. **"Attending" means focused plus recent input:** `document.hasFocus()` and pointer, key or touch input within the last 2 minutes. Mere visibility doesn't count: the office's shared desktop runs a browser around the clock, and a hub tab left visible there must not silence the phone.
4. **A test pins the push payload to a numbers-only schema;** the service worker builds the words from the numbers.
5. **NotificationSent is an audit row** (time and counts) from the first live push, so the product lane can compare its gates before and after.
6. **Every queued Command carries the needs-you state it saw** (`none`, or the question or menu id). The hub judges it on arrival and refuses it as `stale` if the state differs in either direction (S6). AC7 freshness is judged on arrival too. Decision answers stay out of the outbox.
7. **Adding a device:** the issuing or approving Endpoint needs a user verification from the last 5 minutes; a code shows on both screens; the approval screen shows what the hub knows of the requester; every active Endpoint is told; the new Endpoint starts with no step-up credit (AC10–AC13). The reason: linked-device QR phishing has been the most-used way to take over Signal accounts (Google Threat Intelligence, February 2025, via secondary reports cited in §12).
8. **AC1 and AC2 hold unchanged** for the new token sources.
9. **K-1:** in the context map, only an Answer to a policy Ask, given with a fresh step-up, becomes a Mandate; in ADR-0006, an id not yet on the manager's list is "settled, with no Decision" after its grace period. Committed separately.

## Consequences

- **Good:** the hub survives a bad frame, a throw in a socket handler and a schema change; the phone notices a dead socket within seconds; a message is never lost to a reload and never typed twice by a restart; the principal reads where he left off on any device; he can add a device without the box; he hears about a waiting decision without opening the app.
- **More state on the hub:** sends, uploads, read marks, mute, link requests and push subscriptions become tables, each added by a numbered migration.
- **New outside dependency:** a push service (the browser vendor's) carries counts, never content (N1).
- **Owner QA only:** the real phone's push opt-in and a real passkey on a second device can't be automated here.
