The manager and its lanes on tmux

Today one manager, a single Claude Code window, takes every message and every lane event; lanes are tmux windows on any node, reached only through the hub's delivery queue. Three ways to grow that so it stays stable and runs many things at once. All three sit on the same stability layer, at the end. With an API key the shapes stay the same; only what runs in a window changes.

AOne manager, kept quiet

Today's shape, with the noise taken away. Routine lane events go to the board in the hub; the manager is woken only for your messages and for exceptions. A planned handoff each night starts it fresh from a written state, instead of letting its one conversation grow and compact.

Where you write

One Manager chat, the same in the Mac app, the web app, the phone and Telegram. All of it lands in one pane.

What it needs that is new

  • The event filter in the hub
  • A nightly handoff: write state, start fresh
  • Messages queued while it works, shown as queued

Good, and what it costs

  • Smallest change; one mind sees everything
  • Still one queue: a message waits while another topic runs
  • One context for every topic; one pane to lose

BA manager per topicRecommended

A chief and one manager window per topic, side by side in one tmux session. The hub routes each message to its topic; each topic manager starts and steers its own lanes. Parallel directions run in parallel, and each manager's context stays small and on one subject.

Where you write

In the topic's own chat, on its page, in any client. Something new goes to the chief or ⌘K, which files it under a topic or opens one. A teammate writes in the topics shared with them and reaches only that topic's manager.

What it needs that is new

  • A router in the hub: message → topic
  • One delivery queue per manager window
  • The chief for work across topics

Good, and what it costs

  • No waiting across topics; small, focused contexts
  • Matches the cockpit: topic pages, topic chats, sharing by topic
  • More live windows: memory and account limits per node

CShort manager runs, long lanes

No long manager conversation at all. Each direction is a thread with its own record in the hub. A message or an exception becomes a job; a free window from a small pool takes it, reads the record, acts, writes back and ends. Lanes stay long tmux windows, which is where tmux is best: long work you can watch and attach to.

Where you write

In any thread, from any client: a topic, a lane, the inbox. The thread is the memory, not a session, so it does not matter which window answers.

What it needs that is new

  • A record per thread good enough to start from cold
  • A job queue and a pool of manager windows
  • Your call on "one agent in one window" (modules design, section 6.6)

Good, and what it costs

  • Nothing to compact, nothing waits; a crash loses one run
  • Fits API keys best: a run can be a headless call
  • Each run re-reads its record: more tokens, seconds to start

The stability layer, for all three

What keeps tmux sessions alive and honest, whichever shape is chosen. Parts of it already run today (the stamped tmux server, the delivery queue that waits and checks, turn-end hooks); the rest is new.

  1. tmux belongs to the node agent. One server per node, started by the agent's service, stamped so a restart is noticed. Managers and lanes live in separate sessions, so ending work never touches a manager.
  2. The hub holds the desired state. Each lane is a record: topic, brief, engine, session id. Every few seconds the agent makes the windows match: a missing one is recreated and resumed, with backoff and a limit per hour.
  3. Nobody types into a pane directly. Every message passes the delivery queue: it waits for the turn to end and the input to be empty, pastes once, and confirms it in the transcript.
  4. Every turn reports. Hooks mark each turn's end with a status; a lane silent too long is flagged; memory pressure stops new lanes on a node before it swaps.
  5. You can always look. The cockpit's live terminal, or tmux attach -r, read-only, so watching never types into a lane by accident.

What I would do

Build the stability layer first; it pays off in every shape. Then B: it answers "where do people write" the way the cockpit already looks (each topic has its chat, and sharing is by topic), and it removes the waiting across topics without giving up long, attachable sessions. Keep C's idea for the chief later: work across topics is rare, so the chief can run in short runs once threads keep good records.

With an API key instead of a subscription, nothing above changes: a window runs the same Claude Code against the key. In C the manager runs can also be headless calls, with no window at all.
